## 3. 共通ルール

1. 着手前に、同じ概念の既存実装が無いか grep する。あれば拡張する。
2. 比較用のURLスイッチを付ける。既存の `?nobatch=1`、`?norbatch=1`、`?osm=overpass` と同じ流儀にする。
3. 前後比較は性能HUD（⚙ → デバッグ → ⏱ 性能表示）の数値で行う。場所は東京駅、香港（中環）、伊勢原に固定する。
4. 忠実さの原則を守る。建物・道路・線路の位置、形、高さを手続きで作り変えない。
5. 距離や上限の定数を足すときは、対になる定数（生成距離、解放距離、保持距離、カメラの遠方限界）と突き合わせて検算する。
6. 欠測を `|| 0` で既定値に潰さない。
7. `npm test` を通す。純関数は `js/lib/pure.js` に置き、`test/pure.test.js` にテストを足す。
8. 触ったファイルの日付入り経緯コメントは、「なぜ」を1〜2行に縮める。実測値は実装状況の節に写す。
9. 完了したら 11/9版の「実装状況」に節を足し、最後にデプロイ用コマンドを示す。
10. 1段階ごとにデプロイし、実機確認が済んでから次の段階へ進む。

## 4. 段階1: 計測と即効（P-0、P-2、P-3）

**目的**: 生成がどこで止まっているかをスマホの画面で見えるようにし、小さな律速を2つ外す。工数は半日程度。

**作業**

1. HUDに生成系の1行を足す（`js/core/perf-hud.js`）。
   - 表示: `待ち N  休眠 N  生成 N/s  復帰 N/s  1棟 X.XXms  scene N`
   - 待ち = `pendingBuildings.length - pendingBuildingIdx`、休眠 = `dormantCount`、scene = `scene.children.length`。
   - 生成数と復帰数はHUD専用のカウンタを新設する。`part9.js` の `_bgGenerated`、`_bgRevived` はデバッグ表示が2秒ごとに0へ戻すので流用しない。
   - 1棟のmsは、`animate` 内の `addBuilding` 呼び出し（`part9.js:1196`）の前後を `performance.now()` で測り、直近の平均を出す。
   - `perf-hud.js` は他ファイルの変数を `typeof` で確かめてから読む（既存の書き方に合わせる）。
2. タイル表示の建物の棒を分ける（`part9.js` `updateDebugTileOverlay`）。
   - 今は `pending = 待ち行列 + 休眠`（`part9.js:227`）。待ち行列が残るタイルは従来の橙（生成中）、休眠だけが残るタイルは新しい状態 `dormantOnly`（水色）にする。
   - 凡例（`index.html` `#debugTileLegend`）と i18n の `debugLegendHtml` に「休眠（距離・上限）」を足す。
3. 休眠復帰を時間基準にする（`part1.js` `reactivateNearbyDormantBuildings`）。
   - `_dormantCheckFrame % 90 !== 18` の間引きを、前回実行からの経過250ms以上に置き換える。
   - `REVIVE_BUDGET` は、待ち行列が200未満なら従来式（最大600）、200以上なら0。
   - 総数上限まわりの条件（`PERF.bMax` との比較、`_nearCapNow`、`_realRevLim`）は変えない。
   - スイッチ: `?revive=old`。
4. 建物部品をシーン走査の外へ出す（`js/core/bldg-batch.js`）。
   - `BB_HOLDER = new THREE.Group()` を作り、`visible = false`、`updateMatrixWorld = function () {}` とし、`scene.add(BB_HOLDER)` する。
   - 部品を足すヘルパー `bbAttach(part)` を作る。`part.isBBPart` なら `BB_HOLDER.add(part)`、そうでなければ `scene.add(part)`。
   - `part3.js` の `addBuilding` 系で建物部品を `scene.add` している箇所（438、612、680行付近）と、`part2.js` の付属物の追加ヘルパーを `bbAttach` に替える。
   - 解放側で部品を `scene.remove(p)` している箇所（`part1.js:845,1688` 付近）を `if (p.parent) p.parent.remove(p)` に替える。
   - `?nobatch=1` のときは従来どおり `scene` 直下になることを確認する。

**完了条件**

- 東京駅で静止時、`scene` の数が建物数に比例しなくなる。frame ms が悪化しない。
- 鳥モードで直進中、「復帰 N/s」が `?revive=old` より多い。
- 黄色だったタイルが橙と水色に分かれて見える。水色が多ければ、段階2の効果が大きいと確定する。

**やらないこと**: 生成距離や総数上限の値の変更。

**実装メモ（2026-11-11、実装済み・実機確認待ち）**

- HUDは横幅に収めるため2行にした（`待ち N  隔離 N  休眠 N` と `生成 N/s  復帰 N/s  1棟 X.XXms`）。`scene N` は `heap`、`bldg` の行に置いた。「隔離」は地形・道路の確定待ちで退避している建物（`chunkWaitBuildings`、`tileWaitBuildings`）。タイルの橙には前から含まれていたので、HUDにも出して数字が合うようにした。
- 凡例の水色は「休眠」（`index.html`、i18n の ja/en）。
- `BB_HOLDER` は `scene.add` せず孤立ノードにした（走査に入らず、`scene.traverse` の集計にも混ざらない）。holderの `add`・`remove` は番号（`_hi`）で入れ替えて外すO(1)にした。three.js標準の `remove` は `indexOf` + `splice` でO(n)で、数万件の解放では数十msかかるため。補助関数は `js/lib/pure.js` の `idxPush`、`idxSwapRemove`。
- 道路・看板・外形ポリゴン建物の部品（`RBPart`、`road-batch.js`）も同じ仕組みの `RB_HOLDER` に入れた（holderは共通の `makePartsHolder`、追加は `rbAttach`）。当初の指示書は建物部品だけだったが、これを外すと `scene` の数が道路と外形建物の分だけ残るため。`generateChunk` の数え方は建物部品（`BB_HOLDER`）だけが対象。以前は道路の作り直しがチャンクの解放に偶然巻き込まれていたが、道路は距離で別に解放されるので影響しない。
- `generateChunk`（`part8.js`）は、増えた部品を `scene.children` に加えて `BB_HOLDER.children` の増加分からも集める。チャンクのアンロードも `p.parent.remove` に替えた。
- 復帰の予算は `js/lib/pure.js` の `reviveBudget`（単体テストあり）。250ms周期になったので、`_freedThisCycle` は使うたびに0へ戻し、下限は30/回から5/回に換算した。
- 検証: `npm test`（構文20/20、単体9件）。holderの追加・解放・チャンクの数え方は node 上のモックで確認した（6万個から2万個を外して12ms）。ブラウザでの動作は未確認。
- **追補（2026-11-12、実機HUDで発見）**: 復帰だけ高層（h>40）を1.6倍遠く（÷2.56）まで復帰させていたが、生成ループ（`part9.js`）は一律 `BUILDING_GEN_DIST_REAL`（2,200m）で休眠へ戻すため、遠い高層が「復帰→即休眠」を毎秒1,000件超くり返し、待ち行列が常に埋まってFPSが30に張り付いていた（2026-07-21の高層緩和の追加以来の潜在バグ。段階1の250msゲートで頻度が増えて顕在化）。復帰側の緩和を削除して生成ループと同じ判定にした。HUDに `戻し N/s`（生成ループが休眠へ戻した数）を足した。**復帰/s と 戻し/s が同じ値で続くなら判定の食い違い**。

## 5. 段階2: 遠景LOD（R-3、P-1）

**目的**: まだ本体が建っていない実建物（待ち行列、休眠）を箱で描き、移動に生成が追いつかないときの空白と、密集地の上限による欠けを無くす。本書で最も効果が大きい。

**前提**: 段階1（効果を数値で確かめるため）。なお2026-11-12に復帰側の高層緩和を外したので、2,200mより遠い高層は本体が建たない（従来も実際には建っていなかった）。遠景LODは高層を含めて2,200m〜3,200mを受け持つ。

**作業**

1. 高さを決定的にする（R-3）。
   - `part8.js` `processTileData` 内、階数と高さを決める2行（`part8.js:638-639`）の `Math.random()` を、要素IDを種にした乱数に替える。
   - 乱数は `js/lib/pure.js` に純関数として置く（`part3.js:272` 付近の mulberry32 と同じ方式）。テスト「同じIDなら同じ値、範囲内に収まる」を足す。
2. 見た目の決め方を共用する。
   - `addBuilding` の冒頭で種別（kind）と壁色を決めている部分（`part3.js:518-577` 付近）を、副作用の無い関数 `bldgLook(desc)` に切り出す。返すのは kind、壁色、列数、階数。`addBuilding` もこの関数を使う。
3. 遠景用のAPIを足す（`js/core/bldg-batch.js`）。
   - `bbFarAdd(desc)`: 箱1つを遠景用の `InstancedMesh` に書き、ハンドルを返す。セルは `BB_CELL`（500m）。形状は既存の外壁用の単位箱（`_bbBaseGeo` の `'F'`）、材質は `bbFacadeTpl(kind)`。属性 `aObj`、`aCol` の詰め方は `_bbWrite` と同じにする。棟ごとの `Object3D` は作らない。
   - `bbFarRemove(handle)`: `_bbUnregister` と同じく、末尾と入れ替えて詰める。
   - 地面の高さは追加時に `getGroundY` を1回呼んで決める。
   - 視錐台カリングは既存の `bbUpdate` のセル単位の仕組みに載せる。
4. 記述子の一生に繋ぐ。方針は「実建物はデータが届いた時点でまず箱で出し、本体が建つ直前に箱を外す」。待ち行列で待っている間も、休眠中も、箱が見えている状態にする。
   - 入口: 実建物（`b.real`）の記述子が最初に待ち行列へ入る所（`part8.js` `processTileData` が `pendingBuildings` に積む箇所）と `dormantAdd`。ハンドルを `b._far` に持たせ、既に `b._far` があれば何もしない（復帰と再休眠を往復しても二重に足さない）。
   - 出口1（本体が建つ）: `animate` の生成ループで `addBuilding` を呼ぶ直前（`part9.js:1196` 付近）。道路に合わせて捨てる分岐（`_f.drop`）でも外す。
   - 出口2（記述子を捨てる）: `dormantCount` を減らしている箇所のうち、待ち行列へ戻さず捨てる経路（`part1.js:1823,1839,1882` 付近。`evictFarDormant` ほか）。ゲート待ち（`chunkWaitAdd`、`tileWaitAdd`）の記述子を捨てる経路と、タイルを取り直すときに古い記述子を捨てる経路も grep で洗い出す。
   - 漏れの検出: HUDの「遠景 N」が「待ち + 休眠 + ゲート待ち」のうち実建物の数（間引き分を除く）と一致することを確認する。箱が残り続ける場合は出口の漏れ。
   - 箱は道路への合わせ込み（`fitRealBuildingToRoads`）の前の大きさで出るので、本体に替わるとき幅と奥行きがわずかに縮むことがある。目立つ場合は次の課題にする。
5. 上限と間引き。
   - `PERF` のプリセットに `farMax` を足す（lite 20,000 / std 60,000 / high 150,000）。
   - 箱を出す距離は3,200mまで。プレイヤーから2km超は高さ10m以上の建物だけを箱にする。上限に達したら、遠くて低いものから外す。
   - 検算: フォグ濃度0.00056（`part1.js:488`）では、霧の割合が2.2kmで約78%、3kmで約94%、4kmで約99%になる。3.2kmより先は描いても見えない。休眠の保持距離は4,000m（`DORMANT_KEEP_DIST`）、カメラの遠方限界は5,000mなので、3,200mはどちらの内側にも収まる。段階6で高さフォグを入れたら、この距離を見直す。
6. 地形の更新に追従させる。
   - 地形が後から届いて高さが変わったとき（`rebuildBuildingHeight` を呼んでいる経路、`_coastResnap`）に、遠景の箱も `getGroundY` を取り直す。セル単位でまとめて行う。
7. HUDに `遠景 N` を足す。スイッチ: `?farlod=0`。

**完了条件**

- 東京駅と香港で上昇したとき、遠くの建物の欠けが埋まり、タイル表示の水色のタイルにも箱が立っている。
- 箱から本体へ切り替わるとき、位置・高さ・壁色が変わらない。空白のフレームが出ない。
- frame ms の悪化が2ms以内（東京駅、std設定）。超える場合は `farMax` と高さの足切りで調整する。

**やらないこと**: 箱への屋根・付属物の追加。当たり判定、ミニマップ、名前表示への登録。

## 6. 段階3: 世界対応（R-2、R-1）

**目的**: 海外でも昼夜と地形が現地に合うようにする。

**作業**

1. 現地時刻（R-2）。
   - `part1.js` `applyTimeOfDay` の `new Date().getHours()` を、地方太陽時に替える。式は「UTCの時刻 + 経度÷15」を0〜24に丸めたもの。経度は `xzToLatLon(player.position.x, player.position.z)` から取る。
   - 計算は純関数にして `js/lib/pure.js` に置き、テストを足す（東経139.7度・UTC 03:00 → 約12.3時、西経74度・UTC 03:00 → 約22.1時）。
   - `_timeOverrideH` があればそちらを優先する（既存どおり）。
   - 更新の契機は、既存の毎分の更新に加えて地図ジャンプの完了時。
   - スイッチ: `?localtime=0`。
2. 海外の標高（R-1）。
   - `part5.js` の国土地理院タイル読み取り（`_gsiFetchPass` とその周辺）と同じ構造で、Terrariumタイルの読み取りを足す。
   - URL: `https://s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png`。標高 = `R×256 + G + B÷256 − 32768`。ズームは12（日本の緯度で1画素あたり約30m）。
   - 使う場面: 国土地理院のタイルが1点も当たらなかったバッチ（今は opentopodata へ回している箇所）。国内は国土地理院を優先のまま。
   - opentopodata（`/api/elevation`）は、Terrariumの取得に失敗した点だけの最後の保険として残す。
   - 最初に確認すること: ブラウザから取得して画素を読めるか（CORS）。読めない場合はサーバーに `/api/terrarium` のプロキシを足す（`server.js` の既存プロキシと同じ形）。
   - 海域は海底の深さ（負の値）が入る。海の判定はベクタータイルの海面ポリゴンで行う既存の処理に任せ、標高は陸の高さとしてだけ使う。
   - 画面左下の出典表示に Terrain Tiles の出典を足す。
   - スイッチ: `?dem=legacy`。

**完了条件**

- 日本の夜に香港とニューヨークへ飛ぶと、空がそれぞれの現地時刻になる。
- 海外で `/api/elevation` への要求がほぼ出ない（ブラウザの通信一覧で確認）。
- 香港の海岸線と海面が、変更前より悪化しない（11/9版の追補「香港で水の境界が四角く欠ける」の確認場所: 尖沙咀）。

**やらないこと**: 標高の採取間隔の変更（段階7で扱う）。

## 7. 段階4: 生成の高速化（P-4、P-5）

**目的**: タイル到着時のカクつきを減らし、1フレームで建つ棟数を増やす。

**作業**

1. 変換をWorkerへ（P-4）。
   - `js/core/vt-worker.js` を新設し、`importScripts('vt.js')` で読み、`vtLoadBatch` を実行して結果を返す。
   - メイン側の `vtLoadBatch` は Worker への依頼に差し替える。失敗時の扱い（`vtNoteFail`、Overpassへのフォールバック判定）はメイン側に残す。
   - `localStorage` を使うURLテンプレートの取得（`_vtTemplate`）はメイン側で行い、Workerへ引数で渡す。
   - `vt.js` が Worker 内で動くよう、`location` や `localStorage` への直接参照を `typeof` で守る（冒頭の `VT_ON` は既に守られている）。
   - 隣接タイルの継ぎ目情報（`_vtAuxOf`、`_vtChains`）と変換済みの保持（`VT_LRU`）は Worker 側に持つ。
   - 結果のコピーが重い場合（HUDで確認）、座標列を `Float64Array` にして転送する。
   - HUDの vt 行に、メイン側の受け取りにかかったmsを足す。
   - スイッチ: `?vtworker=0`。
2. 建物の2段階生成（P-5）。
   - `addBuilding` を「本体と屋根」と「付属物」に分ける。付属物の記述は `pendingDecor` に積む。
   - 付属物を足す条件: プレイヤーから600m以内。1フレーム2msの予算で、近い順に足す。
   - 付属物の総数制限 `detailOK`（`part2.js:751`、ミニマップ上の建物が850未満のときだけ真）を、距離基準に置き換える。個別の予算（`lotPaddingBudget` など）は残す。
   - 乱数は本体用と付属物用で種を分ける（同じ建物は、後から飾っても同じ見た目になる）。
   - 建物を解放するときに、未処理の付属物の記述も捨てる。
   - スイッチ: `?decor=sync`。

**完了条件**

- タイル到着時の p95 frame ms が下がる（伊勢原の起動直後と、東京駅へのジャンプ直後）。
- HUDの「1棟」の平均msが下がる。
- 東京駅でも、近くの建物に付属物が出る（今は総数制限でほぼ出ない）。
- 静止して待てば、`?decor=sync` と同じ見た目になる。

**やらないこと**: `processTileData` と建物生成そのもののWorker化（効果を見てから判断する）。

## 8. 段階5: 再訪と配信（P-6、G-3）

**目的**: 一度訪れた街をすぐ出す。起動を速くする。

**作業**

1. 変換済みタイルを IndexedDB に保存する。キーは `z/x/y` とタイルの版（URLテンプレートに含まれる版）。保存はWorker側で行う。期限は30日（Overpass経路の `OSM_TILE_CACHE_TTL` と揃える）。総量に上限を置き、古い順に消す。
2. Service Worker でアプリ本体（HTML、JS、three.js）をキャッシュする。更新漏れを防ぐため、配信するJSにコミットのハッシュをクエリで付ける。
3. `manifest.webmanifest` を足し、ホーム画面から全画面で起動できるようにする。
4. 経路シムで、経路上の到達予定順にタイルを先読みする（G-3。`part10.js` の速度の自己抑制と、`part8.js` の前方先読みに繋ぐ）。

**完了条件**: 二度目に訪れた街で、建物が出始めるまでの時間が明らかに短い。Renderが眠っていても画面が出る。

## 9. 段階6: 見た目の底上げ（R-6、D-2の残り、R-5、P-7）

**目的**: 空から見たときの奥行きと発色を上げる。4項目は独立なので、1つずつ入れて確認する。

1. 高さフォグ: 高度が上がるほど薄くなるフォグと、遠景を空の色へ寄せる処理。既存の水面シェーダー（`_waterOnBeforeCompile`）と同じ `onBeforeCompile` の流儀で、建物・地形・遠景の箱に入れる。スイッチ `?hfog=0`。
2. 接地影: 建物の外形を少し広げた暗い帯を地面に描く。セル単位で1メッシュにまとめる（`road-batch.js` の結合を使う）。スイッチ `?gshadow=0`。
3. 太陽の描画と夕焼けの方角（D-2の残り）: 段階3の現地時刻と緯度から太陽の方角を決め、空に太陽を描く。
4. sRGB出力（R-5）: `renderer.outputEncoding` と色テクスチャの指定を揃え、4つの時間帯で露出とライトを再調整する。スイッチ `?srgb=0`。全体の色が変わるので、単独でデプロイして確認する。
5. 対数深度の比較（P-7）: `?logdepth=0` で `logarithmicDepthBuffer` を切り、near を1.0にする。海面と道路に `polygonOffset` を付ける。高度を上げたときに地形と海面がちらつくなら採用しない。frame ms が2ms以上下がる端末があるときだけ既定を切り替える。

## 10. 段階7: 地形の高解像度化（R-4）

**目的**: 丘、谷、山を実際の形に近づける。効果は大きいが、接地処理の全体に触るので最後に回す。

**前提**: 段階3（標高タイル）、段階2（箱の再スナップ）。

**進め方**

1. まず設計メモ `docs/DESIGN_TERRAIN_LOD.md` を作る。内容は、標高タイルを画素のまま保持する形、`getGroundY` の補間、近景25〜50m・中景100m・遠景200mの同心メッシュ、切り替え境界の継ぎ目、既存の海岸処理（`COAST_NODE_BAND`、`LAND_MIN_ABOVE`、`_coastResnap`）との整合。
2. `getGroundY` に依存する処理（道路、橋、トンネル、建物、水面、樹木、当たり判定）を列挙し、それぞれの確認場所を決める。
3. スイッチ `?terrain=fine` で新旧を切り替えられる形で入れ、既定の切り替えは全確認場所の実機確認後にする。

## 10.5 段階8: 動くものと街路（M-1〜M-5、2026-11-11追加）

**目的**: 止まって見える街に動きと夜の光を足す。空からの夜景と「街が生きている」感じに効く。

**前提**: 段階1（計測）。他の段階とは独立なので、段階2の後ならいつ入れてもよい。5項目も互いに独立で、1つずつ入れて確認する。

**現状（2026-11-11のコード確認）**

- 路面の模様（車線、中央線、歩道、縁石、線路）と横断歩道はある（`part3.js` `realRoadTex`、`addRoad`）。
- 車、電車、歩行者、船、飛行機は無い。
- 信号機は幹線道路の区間の中ほどに1割の確率で立ち、色も乱数で固定（`part4.js` `decorateRoad`）。交差点には立たない。
- 街灯は現実モードには無い（`part2.js` の `POLE_ORB` は江戸・メルヘンだけ）。
- 一方通行のタグはベクタータイルから取れている（`vt.js` `_vtRoadTags`）が、ゲーム側では読んでおらず、道路の記録にも入っていない。
- 車線数は地図データに無く、道幅は道路の格で固定。

**忠実さの線引き**

- 道路・線路・建物の位置と形は一切変えない。足すのは、その上を流れるものと光だけ。
- 車・電車・街灯の位置は実データではなく演出である。まとめて切れるスイッチ `?life=0` を付け、⚙設定にも「街の動き」の切り替えを置く。
- 現実モードだけに入れる。江戸・明治などのモードには入れない。

**作業**

1. M-1 信号を交差点へ。
   - `decorateRoad` の乱数による信号設置をやめ、`addRoad` の交差点検出（`nodeUse` が3になった所。横断歩道と同じ条件）で、幅6m以上の道の交差点に立てる。
   - 灯火は時間で青→黄→赤と切り替える。交差点の座標から決まる位相でずらす。個々の更新はせず、共有の時刻uniformとインスタンスごとの位相でシェーダーに任せる。
2. M-2 街灯。
   - 幅6m以上の道に沿って、約35m間隔で左右交互に置く。柱は既存の `poleP`、灯りは `lampP` を使い、それぞれの上限を検算する（`lampP` は現実モードで700。足りなければ街灯専用のプールを作る）。
   - 夜だけ光らせる。点灯の判定は窓の点灯と同じ値（`FACADE_U.uLitRatio`）に合わせる。
   - 置く位置は区間の座標から決定的に決める（同じ街は毎回同じ並びになる）。
   - 遠くからも道路網が光の点列に見えるよう、灯りは小さな発光の板にして霧の効きを弱める。保持距離は道路と同じにする。
3. M-3 走る車。
   - 新しいファイル `js/core/traffic.js`。車は `InstancedMesh` 1つ（箱の車体、前面に白、後面に赤の発光）。上限は lite 150 / std 400 / high 1,000。
   - 走らせる道は幅6m以上（trunk、primary、secondary、高速道路）。細街路には出さない。
   - 経路は道路の記録（`roadRecords`、`roadGrid`）の区間をたどる。区間の端点で繋がる次の区間を選び、行き止まりなら消して別の場所に出す。左側通行・右側通行は国別の建物プロファイルと同じ国判定で決める。
   - 一方通行を守るため、`processTileData` で `oneway` タグを道路の記録に持たせる。
   - 高さは `getGroundY`、橋の上は区間の `slope`、トンネル区間（`rec.tunnel`）では描かない。
   - 出す範囲はプレイヤーから1.5km以内。範囲外に出た車は範囲内の道へ出し直す。
   - 更新は毎フレーム全台の行列を書くだけにし、道の選び直しは端点に着いた時だけ行う。1フレーム0.5ms以内を目安にする。
   - 時間帯で台数を変える（深夜は少なく、朝夕は多く）。段階3の現地時刻を使う。
4. M-4 走る電車。
   - 線路の記録（type が railway の区間）を端点で繋ぎ、編成（箱を6〜10両）を流す。夜は窓を光らせる。
   - 同じ線路上の編成は間隔を空け、上限は見える範囲で10編成程度。
   - 駅（`addStation` で記録している位置）の近くでは減速して数秒止まる。
   - 複線の上下線は地図上で別の線として入っているので、線ごとに一方向へ流す。向きは線の座標の並びに従う。
   - トンネル区間では描かない。
5. M-5 船と飛行機（任意）。
   - 海面ポリゴンの上に少数の船、上空に航行灯を点けた飛行機を数機。位置も経路も完全に架空なので、M-1〜M-4の実機確認の後に要否を決める。

**完了条件**

- 夜の東京駅と香港の上空から、幹線道路が街灯とヘッドライトの筋で見える。
- 車が建物の中、水の上、道の無い所を走らない。一方通行を逆走しない。橋の上で沈まない。
- 電車が線路から外れない。駅で止まる。
- frame ms の悪化が全体で1.5ms以内（東京駅、std設定）。`?life=0` で変更前と同じ数値に戻る。

**やらないこと**: 歩行者。車線数に合わせた道幅の変更（地図データに車線数が無い）。実際の運行データとの連動。交通ルールの厳密な再現（信号待ち、車間）。

## 11. 保留と理由

| 項目 | 保留の理由 | 再検討の条件 |
|---|---|---|
| C-1 解放経路の一本化、C-2 保守処理のスケジューラ | 構造の整理で、体感は変わらない | 解放漏れのバグが再発したとき |
| B-1の後半（解析と建物生成のWorker化） | 工数が大きい。段階2と4で足りる可能性がある | 段階4の後も「待ち」が減らないとき |
| D-6 three.js更新 | 全描画に影響し、リスクが高い | 色管理や新しい描画機能が必要になったとき |
| E-2 ビルド導入、F-1 モジュール化と型検査、F-3 ブラウザテスト | 開発基盤で、体感は変わらない | 取り違え系のバグが増えたとき |
| R-7 高さの外部データ（PLATEAU、Overture） | ブラウザから範囲指定で取れる配信形態が未確認。事前のタイル化が要る可能性が高い | 段階2の後、推測した高さの不自然さが目立つとき |
| R-8 天気、I-1 ブルーム、I-2 雲、I-4 植生 | 段階6の後に載せる方が調整しやすい | 段階6の完了後 |
| D-5 キャラクター、G-1 マップマッチング、C-4 テーマ整理、E-3 配信基盤、H-3・H-7の残り | 今回の目的（リアルに、サクサク）への寄与が小さい | 個別の要望が出たとき |
