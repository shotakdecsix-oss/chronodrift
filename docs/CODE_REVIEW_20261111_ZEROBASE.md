## 2. 総評

取得はもう律速ではない。残っている問題は、次の3つの設計判断から出ている。

1. **建物の表現が「全部入りか、無しか」の2段階しかない。** 生成距離（std 2,200m）の外と総数上限（std 12,000棟）を超えた分は「休眠」になり、画面に何も出ない（`part9.js:1143,1151`）。東京・香港のような密集地を空から見ると、上限に当たって遠くが欠ける。タイル表示の黄色は、この休眠も「生成中」に数えている（`part9.js:227`）ので、黄色の多くは「待てば出る」ではなく「今の仕組みでは出ない」建物の可能性が高い。
2. **取得後の全工程がメインスレッドで動く。** ベクタータイルのデコードと変換（`vt.js`）、タイル解析（`processTileData` 448行）、建物の組み立て（`addBuilding` 552行）がすべて描画と同じスレッドにある。`new Worker` の使用は0件。建物生成の時間予算は1フレーム8ms（`part9.js:1125`）で、60fpsの1フレーム16.7msの半分を使う。
3. **地形と時刻が「世界中」に追いついていない。** 標高は近景でも約540〜665m間隔でしか採っていない（`part6.js:47-48`）。海外の標高は opentopodata 頼みで、1日1,000回の上限がある（`part5.js:192` のコメント上の値、`server.js:146`）。時刻は端末の時計で、現地時刻ではない（`part1.js:650-651`）。

## 4. 項目ごとの詳細

### P-0 計測の足場

- 根拠: 性能HUD（`js/core/perf-hud.js`）はFPS、描画コール、三角形、ヒープ、建物数、バッチ、ベクタータイルの取得・変換msを出す。生成待ちの量と、どこで止まっているかは出ない。`[buildgen]` の数値はコンソールにしか出ない（`part9.js` の `updateDebugTileOverlay` 末尾）ので、スマホでは見えない。タイル表示は休眠を「生成中」に含める（`part9.js:227`）。
- 提案: HUDに1行足す。待ち行列（`pendingBuildings.length - pendingBuildingIdx`）、休眠数（`dormantCount`）、直近1秒の生成数と復帰数、`addBuilding` の平均ms、`scene.children.length`。タイル表示の建物の棒は、待ち行列が残るタイルを橙、休眠だけ残るタイルを別の色（例: 水色）に分ける。
- 効果: 以降の全項目の前後比較ができる。黄色の正体が確定する。
- 注意: 計測自体が重くならないよう、集計は0.5秒に1回にする。

### P-1 遠景LOD（最優先）

- 根拠: 休眠は記述子（位置・幅・奥行き・高さ・向き・種別）だけを200mセルの格子に持つ（`part8.js:326` `DORMANT_CELL`、`dormantAdd`）。保持距離は4,000m（`part1.js:1807`）。カメラの遠方限界は5,000m（`part1.js:496`）。つまり「描けば見える距離にあるのに描いていない建物」のデータが既に手元にある。
- 提案: 休眠に入った建物を、建物1棟=1インスタンスの箱として `InstancedMesh` に直接書く。`BBPart` のような棟ごとのオブジェクトは作らない。外壁は既存のファサード用シェーダーとアトラス（`bldg-batch.js` の `bbFacadeTpl`）を使い、窓と夜の灯りが近景と同じに見えるようにする。本物の建物として復帰したら箱を消す。
- 効果: 密集地の上限による欠けが埋まり、空からスカイラインが見える。速く飛んでも「何もない空間」に出ない。見た目と軽さの両方に効く。
- 注意:
  - 箱の総数に独自の上限を置く（例: std 60,000）。遠いほど低い建物を省く（例: 2km超は高さ10m以上だけ）。
  - 外形ポリゴンの建物（H-1）も遠景では外接の箱でよい。
  - 当たり判定、ミニマップ、名前表示には登録しない。
  - 地形の高さは箱を置く時点の `getGroundY` 1回で決め、地形更新時の再スナップ対象に含める。
  - 忠実さの原則: 位置・大きさ・高さは実データのままなので原則に反しない。

### P-2 休眠復帰の律速を外す

- 根拠: `reactivateNearbyDormantBuildings` は90フレームに1回だけ動き（`part1.js:1720`）、1回の上限は600棟（`part1.js:1747`）。フレーム数基準なので、重くてFPSが落ちるほど復帰も遅くなる。
- 提案: 周期を時間基準（例: 0.25秒ごと）にし、1回の上限を「待ち行列が空に近いほど多く」に変える。待ち行列が十分あるときは復帰させない。
- 効果: 移動中の近景の埋まりが速くなる。P-1の後は、近景の細部化の速さを決める。
- 注意: 総数上限付近の釣り合い対策（`part1.js:1722-1749` のコメント群）を壊さない。上限まわりの条件はそのまま残す。

### P-3 建物部品をシーン走査の外へ出す

- 根拠: まとめ描画の部品 `BBPart` は `THREE.Object3D` を継承し（`bldg-batch.js:22`）、`scene.add` で直接シーンに入る（`part3.js:438,612,680`）。描画は `InstancedMesh` が担うので部品自体は不可視だが、three.js は毎フレーム、シーン直下の全オブジェクトを行列更新と描画対象の収集で2回たどる。建物12,000棟×部品数だけ空振りの走査が起きる。
- 提案: 部品を `visible=false` の入れ物 `Group` にまとめ、その `Group` の `updateMatrixWorld` を空にする。`added`/`removed` イベントによる登録の仕組み（`bldg-batch.js:31-32`）は入れ物への追加でも動く。
- 効果: 毎フレームの固定費が減る。大きさは未計測なので、P-0 の `scene.children.length` と frame ms で前後比較する。
- 注意: アンロード側が `scene.remove(part)` を前提にしている箇所（`part1.js` の解放処理）を、親を問わない `part.parent.remove(part)` に揃える。

### P-4 デコードと変換をWeb Workerへ

- 根拠: `vt.js` は冒頭で `typeof location === 'undefined'` を見ており（`vt.js:30`）、DOMにもthree.jsにも依存しない作りに近い。コメントにも「スマホは描画・変換でメインスレッドが詰まり応答処理が遅れる」とある（`vt.js:34`）。変換後は数MBになる（`vt.js:35` のコメント上の値）。
- 提案: 取得、PBFデコード、Overpass形式への変換までをWorkerで行い、結果を `postMessage` で返す。まず `vt.js` を丸ごとWorkerで動かす最小構成にする。`processTileData` の移設はその後に判断する。
- 効果: タイル到着時のカクつきが減る。HUDの「変換ms」がメインスレッドから消える。
- 注意: 結果のオブジェクトは構造化複製でコピーされる。コピーが重い場合は座標を `Float64Array` にして転送する。ビルド工程が無いので、Workerは `new Worker('js/core/vt-worker.js')` で読み、`importScripts('vt.js')` する。

### P-5 建物の2段階生成

- 根拠: `addBuilding` は1回の呼び出しで本体、屋根、屋上設備、看板、日除け、室外機、当たり判定、ミニマップ、名前索引まで作る（`part3.js:469-1020`）。付属物の間引きは `detailOK()` の一律判定だけ。
- 提案: 高速移動中と、プレイヤーから遠い建物（例: 600m超）は本体と屋根だけで建て、付属物は「飾り待ち」の列に入れて、近づいたときや止まったときに足す。
- 効果: 1棟あたりの生成時間が減り、8msの予算で建つ数が増える。
- 注意: 乱数は位置から決定的に引いている（`part3.js:272`）ので、後から足しても同じ見た目になるよう、乱数の消費順を本体用と付属物用で分ける。

### P-6 変換済みタイルの保存とPWA化

- 根拠: 変換済みタイルの保持はメモリ上の16枚だけ（`vt.js:35`）。IndexedDBはOverpass経路でしか使っていない（`part8.js`）。`index.html` に manifest と Service Worker は無い。
- 提案: 変換済みタイルをIndexedDBに保存する（キーはz/x/yとタイルの版）。アプリ本体はService Workerでキャッシュする。
- 効果: 再訪した街がすぐ出る。Renderの無料プランの起動待ちの影響も減る。「訪れた場所が残る」機能の土台になる。
- 注意: 保存量に上限を置き、古い順に消す。OSMの更新を反映するため保存期限を持たせる（Overpass経路は30日、`part8.js:1054`）。

### P-7 対数深度バッファの比較

- 根拠: `logarithmicDepthBuffer: true`（`part1.js:476`）。カメラは 0.5〜5,000m（`part1.js:496`）。対数深度は画素ごとに深度を書き換えるため、隠れた画素を早めに捨てる最適化が効きにくくなり、画素数に比例して重くなる。
- 提案: URLスイッチ（例: `?logdepth=0`）で切り替えられるようにし、near を1.0に上げた状態で比較する。
- 効果: 端末次第。画素処理が律速の端末では大きい。
- 注意: 導入理由は、高度を上げたときの地形と海面のちらつき（`part1.js:440-442`）。外す場合は海面・道路に `polygonOffset` が要る。ちらつきが出るなら採用しない。

### P-8 保守スキャンの時間基準化

- 根拠: `animate` は建物・道路・地形・海岸など16種の保守関数を毎フレーム呼び（`part9.js:1204-1235`）、各関数がフレーム数の剰余で間引く。FPSが落ちると全部が同じ比率で遅くなる。
- 提案: 「前回からの経過時間」と「このフレームの残り時間」で動かす小さなスケジューラに集める。
- 効果: 低FPS時の回復が速くなる。挙動が読みやすくなる。
- 注意: P-2 を先にやれば、急ぐ必要は薄い。

### R-1 海外の標高をタイル配信へ

- 根拠: 国内は国土地理院の標高タイルを直接読む（`part5.js:217-235`）。海外は opentopodata をサーバー経由で呼ぶ（`server.js:146`）。同APIには1秒1回・1日1,000回の制限がある（`part5.js:192` のコメント上の値）。サーバーは全利用者で共有なので、世界中を飛ぶ遊び方では枯渇しうる。
- 提案: 海外は AWS の Terrain Tiles（Terrarium形式のPNG）を直接読む。URLは `https://s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png`、標高は `(R×256 + G + B÷256) − 32768`。APIキーは不要。国内のPNG標高タイルの読み取り処理と同じ形で書ける。
- 効果: 回数制限が無くなり、海外の地形取得が速く安定する。R-4 の前提にもなる。
- 注意: 出典の表示が必要。ブラウザから画素を読むにはCORS許可が要る（MapLibreがブラウザから直接使っている実績はあるが、実装時に確認する）。海域は海底の深さが入るので、0m未満は海として扱う既存の処理と整合させる。国内は精度の高い国土地理院を優先のままにする。

### R-2 現地時刻で昼夜を決める

- 根拠: `applyTimeOfDay` は端末の時計（`new Date().getHours()`）を使う（`part1.js:650-651`）。日本の夜に香港へ飛ぶと香港も日本時間の空になる。ニューヨークなら昼夜が逆になる。
- 提案: プレイヤーの経度から地方太陽時を出す（UTC時刻 + 経度÷15 時間）。地図ジャンプ時と一定間隔で更新する。
- 効果: 「今この瞬間のその街」になる。外部データは不要。
- 注意: 手動の時刻指定（`_timeOverrideH`）を優先する。標準時とは最大1〜2時間ずれるが、空の明るさには太陽時の方が合う。

### R-3 高さ不明の建物の階数を決定的に

- 根拠: 高さも階数も無い建物は、国別の範囲から `Math.random()` で階数を引く（`part8.js:638-639`）。読み込むたびに同じ建物の高さが変わる。`Math.random` は `part8.js` に41箇所ある。
- 提案: OSMのID（ベクタータイルでは合成ID）を種にした決定的な乱数に置き換える。
- 効果: 同じ街が毎回同じ姿になる。P-1 の箱と近景の建物の高さも一致する。
- 注意: P-1 より先に入れる（箱と本体で高さが食い違うと、切り替わりで建物が伸び縮みして見える）。

### R-4 地形の高解像度化

- 根拠: 標高の採取は近景で約540〜665m間隔（`part6.js:47-48`）、広域で約1km間隔（`part6.js:31`）。描画メッシュは200m格子（`part5.js:37,49`）。丘や谷はならされる。香港の山や伊勢原の大山のような起伏は実際より鈍くなる。
- 提案: 標高タイルを画素のまま持ち、近景を25〜50m格子で描く。`getGroundY` はタイルの画素から双線形補間で返す。
- 効果: 地形のリアルさが最も変わる。
- 注意: 道路・建物・水面・橋はすべて `getGroundY` に載っている。解像度を変えると全部の接地が動く。R-1 の後、比較スイッチ付きで段階的に入れる。工数もリスクも本書で最大。

### R-5 sRGB出力と色管理

- 根拠: ACESトーンマッピングは有効（`part1.js:482`）だが、`outputEncoding` の指定はコード中に無い（grepで0件）。色の計算と出力の色空間が合っておらず、暗部がつぶれ中間色がくすみやすい。
- 提案: 出力をsRGBにし、色テクスチャにsRGB指定を付ける。
- 効果: 全体の発色が自然になる。
- 注意: 全マテリアルの見え方が変わるので、露出と時間帯の色の再調整が要る。比較スイッチを付ける。

### R-6 高さフォグ、接地影

- 根拠: フォグは距離だけの指数フォグ（`part1.js:488`）。影は全体で無効（`part1.js:481`）。
- 提案: 高度が上がるほど薄くなるフォグ。建物の足元に暗い帯を足す（シェーダー内で高さ0付近を暗くするだけ）。
- 効果: 空からの遠近感と、建物の接地感。
- 注意: P-1 の箱にも同じ処理を入れる。

### R-7 建物高さの外部データ

- 根拠: OSMの建物は高さ情報が無いものが多く、R-3 の推測に頼る。
- 提案: 国内は PLATEAU、海外は Overture Maps を調べる。Overture は高さ・階数の付与を広げているが、付いているのは一部の建物（公式の2026-08リリースノートと建物ガイドで確認）。
- 効果: 住宅地や中層ビル街の高さが実際に近づく。
- 注意: ブラウザから範囲指定で直接取れる配信形態があるかは未確認。データ量が大きいので、採用するなら事前にタイル化して配る仕組みが要る。優先度は低い。

### R-8 現地の天気

- 提案: 現地の現在の天気を取得して雲量・雨・霧に反映する。
- 注意: 利用するAPIの利用条件は未確認。R-2 の後でよい。

### F-1 履歴コメントの移設

## 6. 実装指示

**実装指示の正本は `docs/IMPL_PLAN_20261111.md`。** 11/9版の未着手項目と統合し、遠景LODの設計（データ到着時にまず箱で出す）と描画距離（3,200m）も見直してある。以下は初版の指示で、食い違う場合は正本に従う。

各段階は、そのまま実装依頼として使える。共通の決まりは次のとおり。

- 着手前に、同じ概念の既存実装が無いか grep する。
- 比較用のURLスイッチを必ず付ける（既存の `?nobatch=1` と同じ流儀）。
- 完了条件は性能HUDの数値で書く。
- `npm test` を通し、最後にデプロイ用コマンドを示す。
- 忠実さの原則を守る。位置・形・高さを手続きで作り変えない。

### 段階① P-0 + P-2 + P-3

1. `js/core/perf-hud.js` に1行追加する。内容は「待ち N / 休眠 N / 生成 N/s / 復帰 N/s / 建物1棟 X.XXms / scene N」。生成数と復帰数は `part9.js` の `_bgGenerated`、`_bgRevived` と同じ場所で数える専用カウンタを足す（既存のカウンタは2秒ごとにリセットされるので流用しない）。`addBuilding` の時間は `part9.js:1196` の呼び出しの前後で測る。
2. `part9.js` の `updateDebugTileOverlay`（227行付近）で、待ち行列と休眠を別々に数え、休眠だけ残るタイルに新しい状態 `dormantOnly` と色を割り当てる。`index.html` の凡例（`#debugTileLegend`）と i18n の `debugLegendHtml` に追記する。
3. `part1.js` の `reactivateNearbyDormantBuildings`（1717行）の周期を、フレーム数の剰余から `performance.now()` の経過時間（250ms）に変える。`REVIVE_BUDGET` は、待ち行列が200未満なら最大600、200以上なら0にする。総数上限まわりの条件は変えない。スイッチは `?revive=old`。
4. `js/core/bldg-batch.js` に入れ物 `BB_HOLDER`（`visible=false`、`updateMatrixWorld` は何もしない）を作り、`scene.add(BB_HOLDER)` する。`part3.js:438,612,680` で `BBPart` のときは `BB_HOLDER.add` に変える。解放側の `scene.remove(p)` は `p.parent && p.parent.remove(p)` に揃える。スイッチは既存の `?nobatch=1`。
5. 完了条件: 東京駅で静止時の frame ms が下がるか変わらない。`scene` の数が建物数に比例しなくなる。鳥モードで直進したとき「復帰 N/s」が変更前より増える。黄色だったタイルが橙と新色に分かれて見える。

### 段階② R-3 + P-1

1. R-3: `part8.js:638-639` の2つの `Math.random()` を、要素のIDを種にした決定的な乱数に置き換える。`js/lib/pure.js` に純関数として置き、`test/pure.test.js` に「同じIDなら同じ値」のテストを足す。
2. P-1: `js/core/bldg-batch.js` に遠景用のAPIを足す。
   - `bbFarAdd(desc)`: 記述子（x, z, w, d, h, rot, 種別, 壁色）から箱1つを遠景用 `InstancedMesh` に書き、ハンドルを返す。セルは既存と同じ500m（`BB_CELL`）。材質は `bbFacadeTpl(kind)` を使う。
   - `bbFarRemove(handle)`: 末尾と入れ替えて詰める（既存の `_bbUnregister` と同じ方式）。
3. `part8.js` の `dormantAdd` で `bbFarAdd` を呼び、ハンドルを記述子に持たせる。休眠から出る箇所すべてで `bbFarRemove` を呼ぶ（`part1.js` の `reactivateNearbyDormantBuildings` と `evictFarDormant` のほか、`dormantCount--` を grep して漏れを確認する）。種別と壁色は `addBuilding` の冒頭（`part3.js:518-577`）と同じ決め方を関数に切り出して共用する。
4. 上限を `PERF` に足す（`farMax`: lite 20,000 / std 60,000 / high 150,000）。距離2km超は高さ10m以上だけを箱にする。
5. スイッチは `?farlod=0`。
6. 完了条件: 東京駅と香港で上昇したとき、遠くの建物の欠けが埋まる。箱から本体へ切り替わるときに高さと色が変わらない。frame ms の悪化が2ms以内。HUDに「遠景 N」を足して数を確認する。

### 段階③ R-2 + R-1

1. R-2: `part1.js:650-651` を、プレイヤー位置の経度から求めた地方太陽時に置き換える。緯度経度への変換は既存の関数を使う。`_timeOverrideH` があればそちらを優先する。更新は地図ジャンプ時と60秒ごと。スイッチは `?localtime=0`。
