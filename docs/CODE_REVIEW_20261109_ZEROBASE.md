## 総評

現在の性能上限とバグの多くは、次の3つの設計判断から生まれている。

1. **描画の単位が「1パーツ＝1メッシュ」**: 建物・道路を部品ごとに個別のMeshで描いているため、描画コール数が棟数・本数に比例する。建物総数キャップ、ディテールの抑制、GPUクラッシュ対策など、多くの上限処理はこの制約への対症療法になっている。
2. **重い処理がすべてメインスレッド**: Overpass応答のJSON解析、タイル処理、建物生成、ミニマップ描画を、描画と同じスレッドで行っている。生成中のカクつきの根本原因。
3. **グローバル共有の巨大スクリプト群**: 型検査もテストも無い。「解放漏れ」「プロパティ名の取り違え」系のバグが構造的に再発しやすい。

この3点を置き換えると、性能（描画距離・密度）、見た目（ディテール・地形）、安定性がまとめて上がる。上限値や閾値の調整を続けても、天井そのものはほとんど動かない。

## A. 描画アーキテクチャ

### A-1 描画コールが棟数・本数に比例している
**根拠**
- 建物本体は1棟ごとに `new THREE.Mesh`（part3.js:405）、勾配屋根も別のMesh（part3.js:471）。付属物は `dm()` 経由で1個ずつ `scene.add`（part2.js:505-512。part3.jsの建物描画系に呼び出し61箇所）。
- 道路は道路レコードごとに1つのMesh（part1.js:1143）。
- コード内の実測コメントでは、`renderer.info` の geometries が約18,000（part1.js:1802）。
- 本体は単位形状（UNIT_BOX／共有ファサード箱）を `scale` で伸ばしているだけ（part3.js:396-410）なので、そのままインスタンシングに載せられる。

**提案**
- OSMタイル（1.6km）×（形状・マテリアル）ごとに `InstancedMesh` を1つ持ち、建物本体・屋根・付属物をインスタンスとして登録する。
- 道路は「タイル×マテリアル」単位でジオメトリを結合する。タイルを捨てる時はまとめ描画ごと破棄する（C-1と同じ単位）。

**効果**: 描画コールが数千から数百のオーダーに下がる。建物総数キャップ、ディテール抑制、生成距離の制約の多くを緩められる。

**注意**: 地形更新時のY再スナップ、建物の個別削除、衝突判定がメッシュ参照を前提にしているため、インスタンス番号ベースに書き換える必要がある。

### A-2 壁色をテクスチャに焼き込んでいる
**根拠**: ファサードのキャッシュキーは `kind_color_variant`（part2.js:108）。壁色は棟ごとのランダムな明暗（tintWall、part3.js:137-143）と8段階の量子化（part2.js:1085）を経てテクスチャに描かれるため、色の数だけ canvas テクスチャ（本体＋発光マップ）が増える。コード内の実測コメントでは textures 約1,080（part1.js:1802）。

**提案**: ファサードは無彩色の「明暗＋壁マスク」1組にし、壁色は `material.color`（A-1の後は `instanceColor`）で乗算する。窓まで壁色に染まらないよう、`onBeforeCompile` でマスク部分にだけ色を掛ける。

**効果**: テクスチャが種類×バリアントの数十枚に減り、GPUメモリを大きく節約できる。色数の制約も無くなる。

### A-3 対数深度バッファ
**根拠**: `logarithmicDepthBuffer: true`（part1.js:472）。全フラグメントで深度を書き換えるため、GPUの早期深度テスト（隠れる画素を塗る前に捨てる最適化）が効かない。建物が重なる市街地ほど塗りのコストが増える。

**提案**: 路面・水面は `polygonOffset` と描画順で地形の上に重ねる。near面を0.5mから引き上げ、far面はフォグで見えなくなる距離（現在の濃度で昼は約3〜3.5km）に合わせる。D-6の後なら reversed-Z 深度も候補になる。

**注意**: 道路と地形のちらつきが戻りやすい。A-1の後、F-5の数値で効果を測ってから判断する。

### A-4 遠景LODが無い
**根拠**: `THREE.LOD` の使用はゼロ。生成された建物は、距離に関係なく同じ形状・同じ部品数で描かれる。

**提案**: 300〜500mより遠い建物は「屋根・付属物なし、テクスチャ1枚」の簡略版にする（A-1のまとめ描画と相性が良い）。付属物は近景だけで表示する。

**効果**: ディテールの総数制限を「近くは常に出す」形に変えられる。

## B. データパイプライン

### B-1 取得・解析・生成がメインスレッド
**根拠**
- `await res.json()`（part8.js:1633）の直後に `processTileData`（part8.js:374、443行）を同期実行し、`data.elements` を少なくとも5周する（part8.js:416, 428, 556, 705, 721）。
- 建物生成は `animate()` の中で1フレーム最大160棟、時間上限8ms。起動直後30秒と現在地タイルの追い込み中は400棟・14ms（part9.js:1090, 1126）。60fpsの1フレームは16.7msなので、生成中は描画に使える時間がおよそ半分になる。
- `new Worker` の使用はゼロ。

**提案**: Workerで「取得→JSON解析→座標変換→形状生成（Float32Arrayの頂点・行列）」までを行い、Transferableでメインスレッドに渡す。メインスレッドはGPUへの転送とシーン登録だけにする。ファサードとミニマップの canvas 描画は OffscreenCanvas に移せる。

**効果**: 密集地のタイル到着時や移動中のカクつきが根本から消え、生成スループットも上がる。

### B-2 Overpassを主データ源にしている
**根拠**: 1.6km四方のタイルごとにOverpassへ `out geom`（全ノード座標を含むJSON）を問い合わせている（part8.js:15, 996）。経路は主にRender上のプロキシ（server.js `/api/overpass`）で、直接接続のフォールバックもある。応答は冗長なJSONで、Overpass側の混雑・レート制限・IP制限と、プロキシのスリープ・メモリ上限の影響を直接受ける。

**提案**
- 道路・建物・水域・土地利用の基本形状は、OSM由来のベクトルタイルから取る。候補は OpenFreeMap（無料・APIキー不要・OpenMapTilesスキーマ）、または日本域を切り出した PMTiles を静的ホスティングに置く方法。
- スキーマに無いタグ（roof:shape、building:colour など）だけを、プレイヤー近傍に限ってOverpassで後から補う二段構えにする。

**効果**: 初回表示とジャンプ後の待ちが大きく縮む。CDN配信なのでレート制限やIP制限の問題が無くなり、サーバーの役割も小さくなる。

**注意**: 「地図データへの忠実さ最優先」の原則に照らし、切り替え前に同じ範囲でOverpass版との地物の一致を比較する。一般的なOpenMapTiles構成は最大ズーム14（座標の分解能は約0.5m）。OpenMapTilesとOSMの帰属表示が必要。

### B-3 地形が200m格子
**根拠**: 地形メッシュは12km四方を60分割した200m格子（part5.js:37, 49）で、`getGroundY` はこの面をそのまま返す（part5.js:137-138）。一方で取得している標高タイルは国土地理院の dem5a（5m、z15）と dem_png（10m、z14）（part5.js:205-207）。

**提案**: 近景（約1.5km）は10〜25m格子、中景は50m、遠景は現行の200mという同心の多解像度メッシュにする。描画と配置（getGroundY）には必ず同じ高さ関数を使う。既に取得している標高タイルを使うので、通信量は増えない。

**効果**: 谷、河岸段丘、盛土、切通しが実際の地形どおりに出る（伊勢原は大山の麓なので効果が大きい）。

**注意**: 橋・水面・道路の地形への貼り付けなど、getGroundYに依存する処理すべてに影響する。A-1、B-1、F-3（テスト）の後に着手する。

### B-4 PLATEAU（国交省3D都市モデル）
**提案**: 整備済みの都市では、建物を実測の高さ・屋根形状付き（LOD1/LOD2）のモデルに差し替える。オープンデータで、商用利用も可。

**注意**: 伊勢原市が整備対象かは未確認（PLATEAUの配信サイトで確認が必要）。対象外の地域は現行どおりOSMから生成する。

## C. 実行時アーキテクチャ

### C-1 解放処理が種類ごとにバラバラ
**根拠**: `animate()` から毎フレーム、種類別の解放・走査関数を20以上呼んでいる（part9.js:1206-1247。unloadFarBuildings、evictFarDormant、unloadFarRoads、evictFarRoads、unloadFarAreaPolys、compactPools、scanPending… ほか）。新しい種類のオブジェクトを足すたびに専用の解放関数が必要になり、書き忘れがそのままメモリリークになる構造。

**提案**: 生成物はすべて「どのOSMタイル由来か」を持ち、タイルのコンテナ（Group＋まとめ描画＋記録）に登録する。タイルを捨てる時はコンテナごと破棄する。タイルをまたぐ地物（長い道路や川）は参照カウントで管理する。

### C-2 保守処理のスケジューリング
**根拠**: 各関数が独自のフレームカウンタと剰余（例: animate内の `_roadSortFrame % 30 === 0`、drawMinimap の `% 3`）で実行頻度と位相をずらしている。

**提案**: 優先度付きのジョブキューに集約し、「1フレームあたりN ms」の予算で回す。フレーム時間が悪化したら予算を自動で絞る。

### C-3 乱数が決定的でない
**根拠**: `Math.random()` が142箇所。同じ場所に戻ると、壁色・屋根形状・付属物・手続き生成の家の位置が変わる。

**提案**: OSM ID（手続き生成では座標）をシードにした軽量PRNG（mulberry32など）に置き換える。

**効果**: 世界が安定し、生成結果のキャッシュやバグの再現もしやすくなる。

### C-4 テーマ（MODE）分岐の散在
**根拠**: `MODE === 'space'` などの分岐が描画コード全体に散らばっている（part2.jsだけで space 16、edo 12、marchen 9箇所）。

**提案**: パレット、マテリアル、小物、光源、フォグをテーマごとのプロファイルにまとめ、描画コードはプロファイルを引くだけにする。テーマの追加が1ファイルで済み、分岐の漏れも防げる。

## D. グラフィック品質

### D-1 色管理
**根拠**: ACESトーンマッピング（part1.js:478）を使っているのに、sRGB出力（`outputEncoding`）が未設定。全体がくすむ。

**提案**: sRGB出力とテクスチャの色空間指定をセットで入れ、露出とライト強度を4つの時間帯で再調整する。D-6で最新版に上げれば、色管理は既定で有効になる。

### D-2 ライティング
**根拠**
- 環境光（AmbientLight）と平行光源が1つずつだけ（part1.js:579-583）。影が無いため、建物の面ごとの明暗差は平行光源だけが頼り。
- 夜は光源のY座標が `sy*1000 - 150`（part1.js:668）となって地面の下に来る。月明かりが下から当たり、屋根や地面には届かない。

**提案**: HemisphereLight（空の色と地面の照り返し色）に置き換え、太陽と月を別の光源にする。空に太陽を描き、夕焼けにその方角を反映する。high設定ではプレイヤー周辺60〜80mだけ影（シャドウマップ1枚）を落とす。

### D-3 マテリアル
**根拠**: マテリアルはLambert（拡散反射のみ）とBasicだけで、カスタムシェーダーはゼロ（`ShaderMaterial` も `onBeforeCompile` も無い）。

**提案**: 軽量なシェーダーで、水面にフレネル反射・空の映り込み・法線マップのスクロールを、ガラス張りのビルに擬似的な環境反射を足す。

### D-4 フォグ
**根拠**: 一様な FogExp2（part1.js:491）。

**提案**: 高さで減衰するフォグと、遠景を空の色へ寄せる処理（空気遠近）で、遠くの山並みに奥行きを出す。

### D-5 キャラクター
**根拠**: 円柱と球を組み合わせた十数個のMesh（part1.js:2237-2330）。

**提案**: CC0のリグ付きglTFキャラクター（歩く・走る・跳ぶのアニメーション付き）を GLTFLoader と AnimationMixer で動かす。

### D-6 three.js のバージョン
**根拠**: r128をCDNから読み込んでいる（index.html）。

**提案**: 最新版に上げると、BatchedMesh（形の違う物体を1回の描画コールで描ける）、標準の色管理、WebGPURenderer（WebGPU非対応の端末ではWebGL2で動作）が使える。A-1の実装方式に影響するので、A-1より先に方針を決める。

## E. 起動・配信

### E-1 PWA化
**根拠**: manifest も Service Worker も無い（index.html にあるのはiOS用のmetaタグだけ）。

**提案**: Service Workerでアプリ本体（HTML/JS/three.js）をキャッシュし、Renderがスリープ中でもすぐに画面を出す。タイルはIndexedDBのキャッシュから先に描く。ホーム画面に追加すれば、フルスクリーンのアプリとして起動できる。

### E-2 ビルドと読み込み
**根拠**: 15本の `<script>` がすべて同期読み込み（defer/async は0本）。地図パネルを開くまで使わないLeafletが先頭にある。クライアントJS約950KBは圧縮されておらず、バイト数の約38%がコメント行。

**提案**: Viteでバンドル・圧縮・ファイル名のハッシュ化を行う（キャッシュの更新漏れも防げる）。Leafletは地図パネルを初めて開いた時に動的importする。

### E-3 配信基盤
**根拠**: Render無料プランは無操作が約15分続くとスリープし、復帰に30秒〜1分かかる。メモリは512MB。

**提案**: 静的ファイルは Cloudflare Pages や GitHub Pages へ、残るプロキシ（住所検索・標高など）はエッジ関数へ移す。B-2をやれば、プロキシ自体がかなり小さくなる。

## G. 機能・体験

### G-1 GPS追従のマップマッチング
**根拠**: 電車に乗っている時に位置が道路へ吸着される問題を、手動の「線路ロック」トグルで回避している。

**提案**: 手元にある道路・線路のグラフに対して、隠れマルコフモデルとビタビ探索でGPS軌跡を自動で当てはめる。向きは、GPSの進行方向とコンパス（DeviceOrientation）をカルマンフィルタで融合して求める。

### G-2 画面スリープ防止
**根拠**: Wake Lock API の使用はゼロ。GPS追従で歩いている間に画面が消えると、ゲームが止まる。

**提案**: GPS追従と経路シムの間だけ `navigator.wakeLock.request('screen')` を取る。

### G-3 経路シムの先読み
**根拠**: 経路シムは取得キューの滞留を見て自分の速度を絞っている（part10.js:216）。先読みは速度ベースの前方拡張（part8.js `_fwdKMax`）だけ。

**提案**: 経路シムでは先の経路が分かっているので、到達予定の順に経路沿いのタイルを先に取得する。

## F. 開発基盤

### F-1 グローバル共有スクリプトの分割と型検査
**根拠**
- 10ファイル約13,600行が、トップレベルの let/const/var 約570個をグローバルとして共有している。
- 巨大関数: fetchOSMTileBatch 679行、addBuilding 466行、processTileData 443行、generateChunk 290行、animate 268行。

**提案**: ドメインごと（data / world / render / ui / modes）のESモジュールに分け、巨大関数を段階的に分解する。いきなりTypeScriptにせず、JSDoc＋`tsc --checkJs` から始めれば、プロパティ名や型の取り違えを機械的に検出できる。

### F-2 変更履歴コメントの整理（AIのトークン消費にも直結）
**根拠**: 行頭コメントは4,734行（行数の約35%、バイト数の約38%。part8.jsは行数の49%）。大半が日付付きの経緯説明。

**提案**: 経緯は `docs/` の設計記録とgit履歴に移し、コードには「なぜそうするか」を1〜2行だけ残す。

**効果**: 人が読む負担が減る。加えて、AIがコードを読むたびに消費するトークンをおおむね4〜5割減らせる（日本語コメントはコードよりトークン密度が高いため、バイト比以上に効く）。

### F-3 自動テストとCI
**根拠**: package.json のスクリプトは `start` だけ。検証は手動のプローブスクリプト（ルートの DEBUG_PROBE_*.js）に頼っている。

## H. 建物デザイン（追補）

### H-1 実際の外形ポリゴンで建物を立ち上げる
**根拠**: 実OSM建物は、主方位で回した外接矩形（OBB）に置き換えて描いている（part8.js:595-614）。L字・コの字・中庭のある建物や角が斜めに欠けた建物は、実際より大きな箱になり、隣の建物や道路に食い込む。

**提案**
- OSMのポリゴン（マルチポリゴンの内側リング＝中庭を含む）を earcut で三角形分割して押し出す。r128 の `ShapeUtils.triangulateShape` でも可能。
- 壁のUVは「壁の実長÷ベイ幅」「高さ÷階高」で振り、窓の並びを実寸に揃える。
- 屋根は、外形が矩形に近い場合（OBBに対する面積の充填率が0.9以上など）だけ現行の切妻・寄棟を載せ、複雑な外形は陸屋根＋パラペットにする。
- 衝突判定もポリゴン判定（pointInPolygon）に寄せる。

**効果**: 「地図データへの忠実さ最優先」の原則に最も直結する。街並みのシルエットが実際の地図と一致する。

**注意**: 建物ごとに固有の形状になるため、インスタンシングではなくタイル単位のジオメトリ結合（A-1）が前提。A-1と同時に設計する。

### H-2 building:part と高さ系タグ（Simple 3D Buildings）
**根拠**: `building:part`、`min_height`、`roof:height`、`roof:levels`、`building:min_level` を一切読んでいない（該当コード0件）。

**提案**: 外形の中に building:part があれば、外形ではなく各パーツを描く。各パーツは min_height〜height で押し出し、roof:shape と roof:height で屋根を載せる。H-1より前でも、パーツごとの箱として先に入れられる。

**効果**: 駅ビル、低層部（基壇）の上に塔が立つ高層ビル、段々状のビル、ドームのある施設が実際の形になる。都心部ほど効く。

### H-3 屋根
**根拠**
- 勾配屋根の高さは短辺×0.38（上限4.2m、part3.js:634-635）で、勾配は約37°。日本の住宅で一般的な3〜5寸勾配（約17〜27°）より急。
- 方形（pyramidal）は寄棟で代用している（part3.js:621）。入母屋は無い。
- 陸屋根の屋上設備（貯水槽・室外機・アンテナ）は、どの建物でも同じ相対位置に置かれる（part3.js:575-580）。
- 陸屋根の天面は箱の上面のままで、屋根材の表現が無い。

**提案**
- 勾配は3〜6寸の範囲で建物ごとに決める（C-3の決定的乱数を使う）。方形と入母屋の形状を追加する。
- 屋上設備は配置をシードで変え、数を屋根面積に比例させる（キュービクル、室外機の列、塔屋＝階段室・機械室）。
- 陸屋根の天面に防水シートの目地や砂利のテクスチャを貼る。住宅の一部（南向きの斜面）には太陽光パネルを載せる。

**効果**: ジャンプ時や鳥瞰で見下ろしたときの印象が大きく変わる。

### H-4 ファサード（外壁）を面・階ごとに作り分ける
**根拠**
- 住宅は1枚のタイル（2階の窓2つ・掃き出し窓・戸袋・玄関。part2.js:107 facadeMat）を、壁1面に丸ごと引き伸ばしている（part3.js:400-403 で縦横1×1）。このため4面すべてに玄関があり、壁が長いほど窓が横に伸び、平屋でも2階の窓が出る。
- 集合住宅とオフィスは「1フロア×1ベイ」のタイルを全階・全面に同じように並べている。1階も最上階も同じで、4面とも同じ。
- 集合住宅のベランダは絵として描かれているだけで、奥行きが無い。

**提案**
- 面ごとに役割を分ける。道路側を正面（玄関・店構え・ベランダ）、反対側を裏面（共用廊下・小窓）、妻側を窓の少ない壁にする。
- 1階と最上階を別タイルにする。1階は店舗・エントランス・ピロティの駐車場、最上階は笠木やコーニスにする。
- 住宅も実寸でタイルを並べ（ベイ約4m、階高約3m）、玄関は正面の1か所だけにする。
- ベランダは、床スラブと手すり壁を実際の形状（薄い箱）で出す。A-1の後はインスタンスなので安い。

**効果**: 「箱に窓の絵を貼った」見た目から抜け出せる。日本の集合住宅らしさ（ベランダ側と廊下側の違い）が出る。

### H-5 窓を1枚ごとに変化させる
**根拠**
- すべての窓が「点灯」として発光マップに描かれ（facadeMat 内の `win(..., true)`）、色も1色（`MODE_CONF.windowC`）。夜はすべての窓が同じ色・同じ明るさで光る。
- 昼のガラスは不透明な暗色の塗り（`'#25303e'`）で、映り込みが無い。

**提案**
- シェーダーで窓1枚ごとにハッシュを取り、点灯率（時刻に応じて3〜6割）、色温度（電球色〜昼白色）、カーテンの有無を変える。
- 昼は、窓の部分にだけ空のグラデーションを視線の角度に応じて映り込ませる。
- high設定では「室内マッピング」（窓の奥に部屋があるように見える視差表現）も選べるようにする。

**効果**: 夜景が劇的に良くなる。テクスチャはほとんど増えず、A-2（無彩色ファサード）と同じシェーダーで実装できる。

### H-6 色と素材のバリエーション
**根拠**
- 商店は全棟が同じオレンジ（0xff8840、part2.js:1158）、住宅は同じベージュ系（0xd4b070、part2.js:1175）に、明暗の揺らぎを足しているだけ。
- 日本向けの国別プロファイルが無い（part2.js:619-636 は香港・米国の個別設定と地域割り当てだけ）。日本で最も多い `building=yes` は既定の配色と屋根のまま。
- 外壁の質感は、ごく薄いノイズ以外に無い。

**提案**
- 日本プロファイルを作る。外壁はサイディング・タイル・モルタル・ALCの配色、屋根は瓦・スレート・ガルバリウム、勾配屋根の比率も日本の実情に合わせる。
- 素材をテクスチャの種類として持つ（サイディングの横目地、タイル張りの目地、打ち放しコンクリートの型枠穴）。
- 経年の汚れ（雨だれ、基礎まわりのくすみ）をシードで加える。

### H-7 日本の街らしい付属物と実店名の看板
**根拠**: 街の小物は電柱・街灯・自販機・ガードレール・看板などがインスタンスで出る（part2.js:841-900）。一方、建物に付く付属物は玄関庇と屋上設備だけ。

**提案**
- 壁付けの室外機、雨樋、集合住宅の外階段、商店の袖看板と日除けテント、ブロック塀・生垣を追加する。
- 商店の看板には、OSMの店名（`name` タグ）を実際に描く。看板は1枚の共有アトラステクスチャにまとめ、描画コールを増やさない。

**効果**: 「どこの国の街か分かる」レベルの日本らしさが出る。店名は実データなので、地図への忠実さの原則にも沿う。

### H-8 接地影
**根拠**: 影が無いため、建物の足元と地面の境目が一直線になり、建物が浮いて見える。

**提案**: 建物の外形を少し広げた暗いリング（接地影）を地面に描く。A-1の後は1タイルにつき1メッシュで足りる。壁の下端1mを暗くするグラデーションも効く。high設定では、D-2の近距離シャドウマップと併用する。

## I. グラフィック（追補）

### I-1 夜の発光にブルーム
**提案**: 窓・街灯・信号の明るい部分だけを滲ませる。モバイルでは縮小したバッファで1回だけかける。high設定のみ。

### I-2 空と雲
**根拠**: 空は canvas のグラデーションで、毎分描き直している（part1.js の applyTimeOfDay）。
**提案**: 物理ベースの空（three.js の Sky シェーダー）に、2Dの雲レイヤーを重ねる。朝夕は雲が染まるようにする。

### I-3 天気
**提案**: 雨（パーティクル＋濡れた路面の反射）と霧の日を追加する。実際の天気APIと連動させることもできる。

### I-4 植生
**根拠**: 木は幹の円柱と葉の球のインスタンス（part2.js:854, 882）。
**提案**: 十字に組んだ板と透過テクスチャで、樹種ごとの樹形を出す。OSMの `species` / `genus`（例: サクラ属）を読めば、春に桜を咲かせるなどの季節表現もできる。

## 推奨する順序

1. **計測と足場（小さく、すぐ）**: F-5 → F-4 → F-2 → G-2 → D-2 → E-2の一部（defer、Leafletの遅延読み込み）
2. **安全網**: F-3 → F-1（段階的に）。D-6（three.jsの更新）の方針もここで決める
3. **性能の本丸**: A-2 → A-1 → C-1 → B-1 → C-2 → C-3 → A-4（A-3は計測しながら判断）
4. **データと見た目の高度化**: B-2（Overpass版との一致比較を経て切り替え）→ E-1 → E-3 → B-3 → D-1 → D-3 → D-4 → D-5 → G-1 → G-3 → B-4

3まで終われば、建物の総数キャップ、ディテールの抑制、生成距離の制限の多くが不要になり、4の高度化を性能の心配なく載せられる。

### 建物・見た目の改善の順序

- **今の構造のまますぐ効く**: H-6 → H-3（勾配と屋上設備の配置）→ H-8 → D-2
- **A-2（無彩色ファサード＋シェーダー）と同時に**: H-5 → H-4
- **A-1（タイル単位のまとめ描画）と同時に**: H-1 → H-2 → H-7
- **その後**: I-2 → I-4 → I-3 → I-1
