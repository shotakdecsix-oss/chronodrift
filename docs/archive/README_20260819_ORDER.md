## C-1 を見送った理由(再検討しないための記録)

調査の結果、**クラッシュからの復帰機能は既に完成していた**:

- `part9.js:1299` の `setInterval(saveLastPos, 10000)` が、プレイ中ずっと10秒おきに
  緯度経度・camYaw・player.rotation.y を保存している(`part1.js:359`)。
- コメントに「クラッシュ・タブ強制終了からの再開用(ユーザー要望)」と明記。2026-07-24追加。
- **したがって今も、クラッシュ後に手動で再読み込みすれば10秒前の場所と向きに戻る。**

C-1 で増えるのは「手動リロードが不要になる」「モードも復元される」「状況が記録される」の3点だけ。
さらに **`webglcontextlost` が飛ぶのはGPU側で落ちた回のみ**で、レンダラプロセスOOM
(0.8GB→1.5GBで落ちる観測あり)ではJSが動けず自動リロードは発火しない。
自動リロードを入れると、`document.title = '!! GL CONTEXT LOST !!'` によるクラッシュ種別の
判別という現在の計測手段も失われる。

→ **費用対効果が8項目中で最小と判断し、見送り。** ファイル `IMPL_PROMPT_20260819_01_*.md` は不要。

## 順番の理由

- **1〜4は独立**していて、どれから始めてもよい。全部「既にあるものに繋ぐ / 表示を足す」だけなので安全。
- **5(モード統合)は6・7より先**。アルバムを新モードとして足す前に、バッジの受け皿を作っておく。
- **6(山影)は Phase 1 だけをまず単独でデプロイ**。Phase 2(camera.far)は z-fighting のリスクがあるので必ず別回。
- **7(アルバム)は最後**。唯一のゼロからの実装で、2(近傍探索)と5(モード登録)を流用できる。

## 全部に共通する約束

1. **着手前に、指示書の冒頭にある grep を必ず実行する。** 今回の調査で「A-1(地名表示)」「B-1(時刻連動)」
   「C-1(クラッシュ復帰)」の3つが既に実装済みだったことが判明している。このプロジェクトは10ファイルに
   機能が散っていて、知らずに二重実装するリスクが高い。
2. **`farMesh` / `farNodeY` / `farSurfaceY` / `getGroundY` には触らない。** 水面・地形・海岸線の合意事項が
   すべてそこに集約されている。新機能は必ず「加算する新しいレイヤー」として作る。
3. **数を増やす機能には、必ず専用の上限を同時に設計する**(ラベル、写真、板ポリゴン)。`detailOK()` だけでは足りない。
4. **文言は必ず i18n(`t()` / `I18N`、`part1.js` 冒頭)経由**。ja / en の両方を直す。自前辞書を作らない。
5. **タップ判定は `touchend` 起点**に統一する(横向きでタップが効かない不具合の前科あり)。
6. **PC の Chrome DevTools を最初から使う。** 4(landuse)・6(z-fighting)は実機を待たずに PC で判定できる。
7. **欠測値を `|| 0` で潰さない。** 橋の水没バグを6回すり抜けさせた真因。
8. 実装後は毎回デプロイコマンドを出す:
   ```
   cd C:\Users\Shoichi\Desktop\isehara-game; git add -A; git commit -m "..."; git push origin main
   ```
