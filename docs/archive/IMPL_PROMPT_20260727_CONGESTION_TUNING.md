# 実装指示: 自己渋滞の解消(渋滞チューニング再較正+リクエスト数削減)

## 背景

`IMPL_PROMPT_20260726_TILE_SPLIT_FIXES.md` の修正後も「tier1/2で緑赤灰→緑緑赤、緑緑赤→緑緑黄の両方が遅すぎる」症状が継続。レビューの結論は、個別バグではなく**リクエスト数が増えた現状に渋滞対策の較正が合っていない自己渋滞**:

- 通常のエリア充填が約34本(3x3分離18+5x5外周ソロ16)に増えたため、`CONGESTION_BACKLOG=6`が常時超過し、全ソロクエリが5秒打ち切りされる(密集地の正常応答2〜10秒を殺す)→失敗→バックオフ→再試行が渋滞を自己維持。
- pending増で`MAX_LANES=4`まで拡張→発行3.6req/s > Overpass 2スロット/IP→429→クライアントの`osmGlobalCooldownUntil`(30〜120秒)で全タイル凍結の繰り返し。
- リクエスト数自体も多い(5x5外周の全ソロ化は、tier3が別優先度帯に分離された今、前提が消えている)。

対象: `server/server.js`、`js/legacy/part8.js`。

## 進め方

**Step A(サーバーのみ)→ push → 実機確認 → Step B(クライアントのみ)→ push → 実機確認。**
Step C は A/B の効果を実機確認した後、まだ遅ければ着手(今回は実装しない)。
デプロイタイムスタンプ更新を忘れない。pushコマンドは `;` 区切り(PowerShell 5.x)。
実装前に該当箇所の現状コードを読み、本書と実態がずれていたら実態を優先して差分を報告。

## Step A: サーバーの渋滞対策の再較正

### A-1. 詰まり検出の閾値と短縮タイムアウトの緩和

**場所**: server.js 冒頭の定数(L36付近)と `fetchUpstream` 内の congested 判定(L489付近)

- `CONGESTION_BACKLOG`: 6 → **20**(平常のエリア充填(30本超)を「詰まり」と誤認しないため)
- `CONGESTED_TIMEOUT_MS_SOLO`: 5000 → **12000**(密集地のソロ正常応答2〜10秒を打ち切らないため)
- `CONGESTED_TIMEOUT_MS_BATCH`: 20000 のまま
- **blocking/near優先度のリクエストは短縮タイムアウトの対象外にする**: congested でも `opts.priority` が 'blocking' か 'near' なら `UPSTREAM_TIMEOUT_MS`(45秒)を使う。プレイヤーが直接待っているクエリを詰まり時に率先して殺すのは逆効果のため。priority は既に `fetchUpstream` まで届いている(`opts.priority`、Phase3実装参照)。

### A-2. レーン数の上限を上流実態に合わせる

**場所**: server.js `MAX_LANES`(L312付近)

- `MAX_LANES`: 4 → **2**。overpass-api.de は1IPあたり実質2スロットで、3〜4本目は429を誘発してクライアント全体凍結(グローバルクールダウン)を招くだけ。弾力拡張のロジック自体は残してよい(BASE_LANES=2, MAX_LANES=2 なら実質固定2)。
- 併せて、予約レーン(0番=blocking/near優先)の構図は維持されることを確認(BASE_LANES=2なので0番=予約・1番=汎用のまま)。

**注**: スループットを上げたい場合の正攻法はレーン増ではなくミラー(kumi.systems等、別ホスト=別レート制限枠)への振り分けだが、過去の実測でミラーが常時タイムアウトだった経緯([[project_isehara_game_overpass_mirror_experiment]]、server.js L66コメント)があるため今回は触らない。

### Step A 実機確認観点

1. Renderログで「upstream hard timeout」「HTTP 429」の頻度が下がる
2. 密集地でtier1/2の緑赤灰→緑緑赤が体感で明確に短縮される
3. コンソールで `osmGlobalCooldownUntil` 系のクールダウン発動(429起因の全停止)が減る

## Step B: 5x5外周(tier3)をまとめクエリに戻す

**場所**: part8.js `fetchOSMTileBatch` の `nearSolo` 判定(L830付近、`NEAR_TIER_R` を参照している行)

**背景**: 「5x5全部ソロ」(2026-07-25の修正)は、当時tier3が最優先帯にいながら重い3枚まとめで失敗を繰り返し3並列を占有していたことへの対処。現在はtier3が別帯(-9000、tier2より明確に下)へ分離済みで、この前提が消えている。ソロ16本はリクエスト数の主要因。

**修正**: `nearSolo` の判定距離を `NEAR_TIER_R`(2、5x5)→ `NEAR_SPLIT_TIER_R`(1、3x3)に変更。これで:

- tier1+2(3x3)= 分離ジョブ(road/building各ソロ)… 変更なし
- tier3(5x5の外周16枚)= 従来の複合3枚まとめ(`OSM_TILE_BATCH=3`)… 16本→約6本
- エリア充填の総リクエスト数 約34本→約24本

**注意**:
- 分離ジョブ(kind='road'|'building')は従来通り常にソロ(`isSplitJob`分岐)。今回の変更は複合クエリの範囲判定のみ。
- tier3の3枚まとめは priority='far' としてサーバーへ送られ、予約レーン0を使わない(Phase3の構図が正しく効く)。変更不要のはずだが確認すること。
- まとめクエリの失敗時バッチ縮小ロジック(`nextFailCount >= 2` で1枚化)は既存のまま活かす。

### Step B 実機確認観点

4. デバッグオーバーレイで、tier3(外周)がまとめて緑化する挙動に戻る(tier2より先に完了しないこと=優先度帯分離が効いていること)
5. エリア充填全体(5x5が全緑になるまで)の時間が短縮される
6. 密集地でtier3の3枚まとめが504を連発しない(するようなら報告のみ。対処はStep C以降で検討)
