## 総評

**モデリングは既にかなり良い。** 建物は屋根形状（陸屋根の parapet、切妻・寄棟・片流れ、`roof:shape` タグ反映、国別の屋根形状ウェイト）、屋上設備（受水槽・室外機・煙突・サイロ・のこぎり屋根）まで作り込まれているし、道路テクスチャは歩道・縁石・路側線・中央線（国道は黄色2本、主要地方道は黄色1本、生活道路は白線のみ）・バラスト＋枕木＋レールまで描き分けている。ここは触る必要がない。

**リアルさのボトルネックは、モデリングの手前と外側にある。** 具体的には5層:

1. **描画パイプライン** — sRGB出力が未設定・影が一切ない・異方性フィルタなし。せっかく描き込んだテクスチャとディテールが画面に届いていない。
2. **OSMタグの取りこぼし** — 実際に読んでいるタグは26種類だけ。`tunnel` を見ていないので地下鉄が地表を走り、`height` を見ていないので高層ビルの高さがランダム。
3. **地形データの使い残し** — **5mメッシュのDEMをダウンロードして、545m間隔でしかサンプルしていない**。ここが最大の伸びしろ。
4. **挙動とスケール** — 最低移動速度が18km/h。「歩き」が存在せず、その副作用で足音機能が丸ごと死んでいる。
5. **現実モードに残った幻想モードの遺物** — 松明の点光源6個が現実モードでも生成されている。

以下、**低コストで効く順**ではなく**層ごと**にまとめ、末尾に優先順位表を置く。

## A. 描画パイプライン — 描き込んだものが画面に出ていない

### A-1. `outputEncoding` が未設定（＝ガンマ補正されていない）★

**該当**: `part1.js:472-479`、`index.html:657`（three.js **r128**）

```js
const renderer = new THREE.WebGLRenderer({ canvas, antialias: GFX.aa, logarithmicDepthBuffer: true });
renderer.shadowMap.enabled = false;
renderer.toneMapping = THREE.ACESFilmicToneMapping;
renderer.toneMappingExposure = 0.9;
// ← outputEncoding の設定が無い
```

コードベース全体を grep しても `outputEncoding` / `sRGBEncoding` / `gammaFactor` / `colorSpace` が**1箇所も出てこない**。three.js r128 の `WebGLRenderer.outputEncoding` の既定値は `LinearEncoding` なので、**ACESトーンマッピングの結果をsRGB伝達関数にかけずにそのままフレームバッファへ出している**。結果として、意図した色より中間調が沈んだ・彩度の低い絵になる。

three.js を使ったプロジェクトで最も典型的な色パイプラインの取りこぼし。「なんとなく全体がくすんで見える」原因の第一候補。

**注意（重要）**: r128 には自動カラーマネジメント（r152以降の `ColorManagement`）が無いため、`0xd8d0c0` のようなマテリアル色定数はリニア値としてそのまま扱われている。`outputEncoding = sRGBEncoding` を入れると**全体が明るく・コントラストが変わる**ので、
- 全カラーテクスチャ（`facadeMat` の map/emissiveMap、`realRoadTex`、`roofTex`、`meijiTex`、空、地形）に `.encoding = THREE.sRGBEncoding` を付ける
- `toneMappingExposure`、`ambientLight.intensity`、`moonLight.intensity`、`DAY_KF` の各 intensity を再調整する

までがワンセット。**単独で入れて終わりにできる修正ではない**ので、他の項目より後に、時刻プリセット4種（夜/朝/昼/夕）すべてで見比べながら進めるのが安全。

### A-2. 影が一切ない ★

**該当**: `part1.js:477` `renderer.shadowMap.enabled = false;`

建物も木も小物も、地面にも互いにも影を落とさない。「オブジェクトが地面に貼り付いて見える」「街に奥行きがない」の最大の原因はこれ。`part1.js:577` のコメントにある通り、影を切ったのは意図的な性能判断（CODE_REVIEW_20260717 P2）。

realism を上げたい場合の現実的な選択肢は3つ、コスト順に:

1. **ブロブ影** — 建物・木の足元に半透明の黒い板を1枚置く。インスタンス化すればドローコールは増えない。接地感だけなら劇的に改善する。最安。
2. **プレイヤー周辺限定の1枚シャドウマップ** — `DirectionalLight` のシャドウカメラを全世界ではなく**プレイヤー中心の40〜80m四方**に固定し、1024²程度で焼く。近景の建物影・街路樹の影が出る。遠景は影なしのままだがフォグで隠れる。中コスト。
3. 本格的なCSM（カスケード） — このプロジェクトの規模では過剰。

**性能レビューとの関係**: 影を有効にするとシーン走査が1回増える。前回レビューの `logGpuBytes`（10秒ごとの scene.traverse）や保守処理の位相集中を先に片付けてからの方が、影のコストを正しく評価できる。

### A-3. 異方性フィルタリングが未設定 ★★（最も費用対効果が高い）

**該当**: 全テクスチャ。`wrapS/wrapT` は設定しているが `anisotropy` は grep で**0件**。

`realRoadTex`（`part3.js:745-825`）は 128×256 に歩道・縁石・路側線・中央線・車線破線・わだち・バラスト・枕木・レールまで描き込んである。ところが**歩いている時の路面は常に浅い視線角**で見るため、ミップマップで手前から数メートル先までしか解像されず、その先は灰色に潰れる。せっかくの描き込みが視界のほとんどで見えていない。

```js
// 各テクスチャ生成箇所に1行
tex.anisotropy = renderer.capabilities.getMaxAnisotropy();  // 通常 16
```

GPU的にはほぼ無料（サンプリングコストのみ、メモリ増加なし）。**路面・屋根・地形の見え方が最も大きく変わる1行**。対象は `realRoadTex`(part3:745)、`roofTex`(part2:444)、`meijiTex`(part3:996)、水面(part4:323)、遠景海面(part6:406)、`facadeMat` の map(part2:296)。

### A-4. `HemisphereLight` が無い

**該当**: `part1.js:573-577`

```js
const ambientLight = new THREE.AmbientLight(MODE_CONF.ambient, MODE_CONF.ambInt);
const moonLight = new THREE.DirectionalLight(MODE_CONF.moon, 1.8);
```

`AmbientLight` は全方向から完全に一様な光なので、面の向きによる明暗差が消える。屋外の見え方は実際には「上＝空の青い光／下＝地面の反射光」という二極の環境光で決まる。`AmbientLight` を `HemisphereLight(skyColor, groundColor, intensity)` に置き換えるだけで、建物の上面と下面、木の上と下に自然な差が出る。**コストはほぼゼロ**（Lambert/Phong シェーダの追加項1つ）。

`DAY_KF`（`part1.js:597-602`）には既に時刻別の `amb` 色があるので、そこに ground 色（昼＝アスファルト灰／夕＝赤みがかった土色）を1つ足すだけで時刻連動もそのまま乗る。

### A-5. 空に太陽・月が無く、夕焼けに方位がない

**該当**: `buildSky` `part1.js:499-524`、`applyTimeOfDay` `part1.js:635-649`

空は 512×512 のキャンバスに縦グラデーション＋下端中心の**放射状グラデーション**を描いて球に貼っている。放射状グラデーションの中心は `(256, 512)` ＝ 球のUVで v=1、つまり**天底**。半径300pxが上へ v≈0.41 まで届くので地平線帯は覆えているが、**回転対称なので全方位が均等に赤くなる**。

実際の夕焼けは西の空だけが赤い。しかも `moonLight` の方位（`part1.js:656-657`）は時刻から計算しているのに、空のglowはそれと連動していない。

- glowの中心を太陽方位に合わせて水平にずらす（キャンバスの x 座標を動かすだけ）
- 太陽ディスク（小さい発光板 or Sprite）を1枚、`moonLight` と同じ方向に置く

の2つで「時刻と方角が空を見れば分かる」状態になる。実在の場所を歩くゲームでは効果が大きい。

### A-6. 夜、太陽光が地面の下から差している

**該当**: `part1.js:656-657`

```js
const ang = (h - 6) / 12 * Math.PI, sy = Math.sin(ang);
moonLight.position.set(Math.cos(ang) * 900, sy * 1000 + (sy < 0 ? -150 : 200), 300);
```

`h`（時刻）が 18時〜翌6時のとき `ang` は π を超え、`sy < 0` になる。真夜中（h=0 または 24）では `sy ≈ -1` → **y ≈ -1150**。`DirectionalLight` は position から原点へ向かう平行光なので、**夜は光が地面の下から上へ向かって差す**。建物の下面や庇の裏が明るくなる。強度が 0.5 と低いので目立ちにくいが、夜景の破綻要因。

夜は月として上空（たとえば太陽の反対側の上空）に置き直すのが正しい。ついでに月は現状「空に見えない」ので、A-5 の太陽ディスクと同じ仕組みで月も出せる。

### A-7. 夜の窓の発光が強すぎる

**該当**: `part1.js:680-684`

```js
const winGlow = winLit * (USES_MEIJI_LANDUSE ? 1.1 : 3.0);
facadeCache.forEach((mat) => {
  const base = mat.userData.baseEmi ?? 0.85;
  mat.emissiveIntensity = base * winGlow;
});
```

現実モードの夜は `0.85 × 3.0 = 2.55`。ACES（exposure 0.9）でも 2.55 のリニア白は完全に飽和するので、窓が一様な純白に飛ぶ。実際の夜の街の窓は、部屋ごとに色温度も明るさもばらついていて、白飛びしているのはごく一部。

- 全体値を 1.2〜1.6 程度に下げる
- 窓色 `MODE_CONF.windowC` を1色固定でなく、`facadeMat` の `variant`/シードごとに電球色〜蛍光灯色でばらす（`facadeMat` は既に決定論的な乱数 `rnd()` を持っている `part2.js:147-149` ので、そこから引くだけ）
- 点灯窓の割合を100%でなく60〜80%にする

この3つで夜景が一気にそれらしくなる。

### A-8. フォグが濃すぎて遠景が存在しないに等しい

**該当**: `part1.js:484`

```js
const WORLD_FOG = new THREE.FogExp2(MODE_CONF.fog, MODE === 'meiji' ? 0.0004 : MODE === 'space' ? 0.00008 : 0.00056);
```

`FogExp2` の残存率は `exp(-(density × d)²)`。density = 0.00056 のとき:

| 距離 | 見え方 |
|---|---|
| 1,000m | 73% 残る |
| 2,000m | 29% 残る |
| 3,000m | 6% 残る |
| 4,000m | 0.7% 残る |

`camera.far = 5000` なのに、**実質的な視界は2.5〜3km**。日本の晴天時の視程は20〜40km ある。この設定だと大山の山塊も相模湾も、都心なら新宿・東京のスカイラインも一切見えない。プロジェクトメモリの「遠景が見えない真因はフォグ」はこれ。

LOD境界や未生成エリアを隠すというフォグ本来の役目はあるが、realism を取るなら:
- density を 0.00018〜0.00025 程度（視程6〜9km）まで下げる
- 隠蔽は「遠景メッシュの頂点色を距離に応じて空色へ寄せる」（＝大気遠近）で代替する。`terrainColorRGB`（`part5.js:146`）と `updateFarMesh` の頂点色ループ（`part5.js:116-125`）に距離ブレンドを1行足すだけで、遠くの山が青みがかって霞む本物の見え方になる

**性能への影響**: フォグを薄くすると遠くのオブジェクトが「見えてしまう」ので、描画距離の設定（`PERF` プリセットの `roadUnload` / `bGenReal`）との整合を取る必要がある。遠景メッシュだけ遠くまで見えて建物が途中で消えると、逆に境界が目立つ。**フォグと描画距離は対で調整する**（メモリの `feedback_pair_check_distance_constants` と同じ話）。

### A-9. 現実モードに松明の点光源が6個ある ★（バグに近い）

**該当**: `part1.js:581-588`

```js
const torchColors = [0xff6a00, 0xff8c40, 0xffaa60];
const torchLights = [];
for (let i = 0; i < 6; i++) {                       // ← MODE のガードが無い
  const pt = new THREE.PointLight(torchColors[i%3], 1.2, 300);
  pt.position.set(Math.random()*2000-1000, 4, Math.random()*2000-1000);
  scene.add(pt);
  torchLights.push(pt);
}
```

`MODE` によるガードが無いので、**現実モードでも生成される**。原点±1000mの範囲にランダム配置、地面から4m、到達半径300m、夜は `intensity = 0.1 + night × 1.1`（`part1.js:661`）＝ 1.2。

つまり**現実の街のど真ん中に、光源のない場所からオレンジ色の光が6箇所漏れている**。しかも位置は固定で、`part6.js:310` で地域移動時に Y だけ再スナップされるが X/Z は据え置き。幻想モード（メルヘン・江戸）の名残がそのまま残っている。

`MODE === 'marchen' || MODE === 'edo'` のときだけ作る、が正しい。夜景の不自然さの直接原因なので、削除の効果はすぐ分かる。

**ついでの性能効果**: Lambert マテリアルで PointLight 6個は全メッシュのシェーダに 6ループぶんの負荷を足している。消すとフラグメント負荷も下がる。

## B. OSMタグの取りこぼし — 「地図データ忠実性を最優先」原則に直結

コード全体で実際に読んでいるOSMタグを機械的に洗い出した結果（`grep -ohE "tags\[['\"][a-z:_]+['\"]\]|tags\.[a-z_]+"`）:

```
building, leisure, amenity, waterway, railway, natural, name, name:ja, name:en,
roof:shape, roof:material, roof:colour, building:levels, building:height, building:colour,
public_transport, landuse, highway, bridge, water, surface, sport, shop, religion, office
```

**26種類のみ。** 以下は全く参照されていない。

### B-1. `tunnel` を一切見ていない ★★（データ忠実性で最大の穴）

grep結果 **0件**。`processTileData`（`part8.js:396-473`）は `tags.bridge` は見ているが `tags.tunnel` は見ていない。

つまり **`tunnel=yes` の道路・鉄道がすべて地表のリボンとして描かれている**:

- **東京・大阪の地下鉄** — 東京メトロ・都営線の多くは `railway=subway` なので取得対象外だが、**JR中央線の一部・総武線地下区間・京葉線・りんかい線・つくばEXなどは `railway=rail` + `tunnel=yes`**。これらが地表を貫いて走る。
- **首都高の地下部・地下道路** — 山手トンネル、外環道など。`highway=motorway` + `tunnel=yes`。
- **山岳部の道路トンネル** — 山肌の斜面に道路リボンが貼り付く。
- **地下街・地下通路** — `highway=footway` + `tunnel=yes`。

しかも B-3 と組み合わさると、地下通路が「4.2m のアスファルト道路」として街を横断する。

#### 方針（2026-08-28 ユーザー合意 → **同日実装済み・実機未確認**）— 「一律スキップ」ではなく、種別と長さで分ける

一律に描かないと、山岳トンネルのところで道がぶつ切りになる。それを避けつつ、実害の大きいケースだけを潰す。

**前提として確認した事実（判断の根拠）**

1. **道路リボンは地形に密着している。** `makeRoadGeo` は `segs = Math.max(1, Math.round(len))` ＝ **1m刻みで頂点を打ち**（`part3.js:1165`）、各頂点で `getGroundY(vx, vz)` を引く（`part3.js:1211`）。だから今の山岳トンネルは「地形に沿った連続した峠道」に見えていて、破綻していない。**消すと素直に損に見えるのは正しい直感。**

2. **`highway=motorway` + `tunnel=yes` は高架になる。** `addRoad` は `tunnel` を見ずに `type === 'motorway'` で `addMotorway` へ分岐する（`part3.js:1255`）。`makeMotorwayGeo` は路面を **地面+7m**（`MWY_H = 7`, `MWY_W = 16`, `part3.js:855`）に置き、防音壁・桁側面・桁裏まで作る。つまり**首都高中央環状線の山手トンネル（約18km）が、渋谷〜池袋の地上に幅16m・高さ7mの高架として出現する**。これは道が途切れるよりはるかに悪い。

3. **トンネルの真上の実建物が消えている。** `addRoadRecord` → `removeBuildingsOverlappingRoad`（`part1.js:802`）は `tunnel` を見ない。地下鉄の直上に、リボン幅＋余裕の帯で建物のない回廊ができる。これは「間違ったものが見える」ではなく**「正しいものが消える」**ので、[[地図データ忠実性を最優先する大原則]] に直接反する。

4. **長い山岳トンネルの「峠道」も遠目だけ。** 標高400mの山を貫くトンネルを地表に描くと水平2kmで400m登る道になる。`ELEV_SCALE = 2.0`（`part5.js:134`）で見た目の勾配はその倍＝**実質40%の壁**。近くで見れば峠道には見えない。

5. **連続性はミニマップで保てる。** `drawMinimap` は `queryRoadGrid`（`part7.js:905`）＝ `roadGrid` を見ており、これは `addRoadRecord` の `roadGridAdd` で埋まる。つまり **roadRecord は作ってメッシュだけ作らない**ようにすれば、3Dに嘘の道を出さずに**ミニマップ上では道がつながったまま**にできる。

**決定表**

| 条件 | 3Dメッシュ | roadRecord | 建物削除・植生除去・小物装飾 |
|---|---|---|---|
| `railway` + tunnel | 作らない | 作る（ミニマップ用） | しない |
| `motorway` + tunnel | 作らない。**`addMotorway` には絶対に渡さない** | 作る | しない |
| その他の道路 + tunnel、way全長 < `TUNNEL_SURFACE_MAX_M` | **従来どおり地表に描く**（アンダーパス・覆道。実際ほぼ地表高さで、連続性の利得が誤差を上回る） | 作る | **する（＝通常の道路とまったく同じ扱い）** |
| その他の道路 + tunnel、way全長 ≥ 閾値 | 作らない | 作る | しない |
| tunnel でない | 従来どおり | 従来どおり | 従来どおり |

> **【2026-08-28・実装時の設計変更】** 当初この行の最終列は「しない」としていたが、実装時に**「描くなら道路として扱う」に改めた**。短いトンネルは地表に見えている以上、そこに建物が重なったり手続き生成の家が上に建ったりしては困る。したがって免除の基準は「トンネルかどうか」ではなく**「3Dメッシュを描かないかどうか（`_noMesh`）」**とし、フラグ1つで全部の分岐を揃えてある。

`TUNNEL_SURFACE_MAX_M` は **const 1つ**にしておく（初期値 150m 程度）。実機で「やっぱり途切れが気になる」となったら 150 → 500 と動かすだけで調整できるようにするのが狙い。**長め（例: 400m）から始めて詰める**進め方でもよい。

**実装メモ（先に潰しておくべき点）**

- **判定**: `tags.tunnel && tags.tunnel !== 'no'`。`covered=yes`（地表の覆いで、地下ではない）は別物なので**混ぜないこと**。
- **way全長**: `processTileData`（`part8.js:396-473`）の way ループで、セグメントループに入る前に `el.geometry` から累積長を出す。橋（`bridgeCum`）で同じ計算を既にやっているので、そのパターンを流用できる。
- **フラグはレコードのフィールドに載せる**: `rec.tunnel = true` を `addRoad` の `rec` 生成時（`part3.js:1312` 付近）に足す。**新しい配列に貯め込まないこと** — 性能レビューで見つかった `railSegs`（書き込み専用のデッドデータ、2026-08-27に削除済み）と同じ轍を踏む。レコードのフィールドなら `evictFarRoads` の破棄にそのまま相乗りできる。
- **★最大の落とし穴: メッシュ無しレコードの無限再投入。** `queueRoadMesh` の呼び出し元は3箇所ある:
  - `addRoad`（`part3.js:1320`）
  - `unloadFarRoads`（`part1.js:1283`）— **`if (!r.mesh || r._dirty) { if (dd <= lim2r) queueRoadMesh(r); }`**。メッシュを持たないレコードを**1.5秒ごとに永久に再投入し続ける**
  - `rebuildRoadsInBounds`（`part1.js:1414`）— NEAR地形更新のたびに `_dirty = true` を立てて再投入

  呼び出し側を3箇所直すのではなく、**`queueRoadMesh` の先頭（`part1.js:1134`）に1行ガードを置く**のが確実:
  ```js
  function queueRoadMesh(r) {
    if (r._noMesh) return;          // ← 追加。トンネル等、そもそもメッシュを作らないレコード
    if (r._q || r._dropped) return;
    ...
  ```
- **建物削除・植生除去の免除**: `removeBuildingsOverlappingRoad`（`part1.js:762`）と `queueVegetationCleanup`（`part1.js:874`）には**既に `if (r.type === 'water') return;` という type ベースの免除の先例がある**。同じ位置に `if (r.tunnel) return;` を足すだけでよい（[[実装前に既存の類似機構を検索]]）。

**Phase 2（任意）: 坑口**

長いトンネルでメッシュを作らない場合、道が山肌で終わる理由を画面上で説明するために、坑口（暗い面1枚）を立てると格段に正しく見える。

**ただし素朴に実装すると失敗する**: OSMのトンネルは複数の way に分割されていることが多いので、**「トンネルwayの端点」に坑口を置くとトンネルの途中に坑口が並ぶ**。真の坑口は「トンネルwayの端点が、非トンネルwayの端点と一致する場所」。`nodeUse`（`part3.js:847`、1m格子に丸めた端点キー）と同じ手法で判定できるが、**タイル境界をまたぐトンネルでは片側しか見えない**という限界が残る。

なので坑口は Phase 1（描画抑止）の実機確認が済んでから、別コミットで扱うのが安全。

**実機での確認場所**

- **山手トンネル（首都高中央環状線、渋谷〜池袋）** — `highway=motorway` + `tunnel=yes`。修正前は**高架が出ているはず**。ここが消えれば修正2の効果が一目で分かる
- **総武線快速の地下区間（東京〜錦糸町）** — `railway=rail` + `tunnel=yes`。修正前は地上に線路（バラスト＋枕木）が出ているはず。**直上の建物が消えているかどうか**も併せて見る
- **短いアンダーパス**（鉄道と交差する道路の掘割）— 閾値以下なので**従来どおり描かれ続けること**を確認する（＝閾値が効いているかの確認）
- いずれも**実際のOSMタグは事前に確認すること**（本レポートの推定であり、検証はしていない）

### B-2. `height` タグを読んでいない ★

**該当**: `part3.js:7-13`

```js
function resolveBuildingHeight(tags) {
  const hTag = parseFloat(tags['building:height']);
  if (Number.isFinite(hTag) && hTag > 0) return hTag;
  const levels = parseInt(tags['building:levels']);
  if (Number.isFinite(levels) && levels > 0) return Math.max(levels * 3, 3);
  return null;
}
```

OSMで建物高さを表す標準タグは **`height`**。`building:height` は非標準の少数派で、`height` の方が圧倒的に多い（特に高層ビル・ランドマークは `height` で入っていることがほとんど）。

つまり現状、**実測高さがOSMに入っている高層ビルの多くが、`levels` かランダム式で建てられている**。都心のスカイラインの忠実性に直結する。

```js
const hTag = parseFloat(tags['height'] ?? tags['building:height']);
```

に相当する1行の追加で効く。`height` は `"120 m"` のように単位付きの値が入ることがあるので `parseFloat` で数値だけ取れる（既に `parseFloat` なので問題ない）が、`"120'"`（フィート）表記が稀にあるので念のため単位判定を入れると堅い。

**ついでに**: `min_height` / `building:min_level`（下駄履き建築・空中回廊の下端）、`roof:levels` / `roof:height`（屋根の高さ）も未使用。優先度は `height` より低い。

| `track` / `path` | unpaved（正しい） | そのまま |

`realRoadTex` に `sidewalk` 用の kind を1つ足すだけで見た目は用意できる（既に `sidewalk()` ヘルパーが `part3.js:765` にある — **メモリの「実装前に既存の類似機構を検索」が効く箇所**）。

### B-4. `lanes` / `width` を使っていない

道路幅がクラスごとの定数（`IS_REAL` で trunk=14 / primary=12 / secondary=9 / tertiary=6.5 / road=4.2 に固定、`part3.js:1270-1277`）。OSMには `lanes=*` と `width=*` が入っている道が多く、特に幹線では実測幅との差が大きい。

`width` があればそれを、無ければ `lanes × 3.25m + 路肩` を使う、という優先順にすると、片側1車線の国道と片側3車線の国道が同じ幅にならなくなる。

### B-5. `layer` を見ていない

立体交差の上下関係が表現できない。`bridge` は見ているので跨線橋・橋は持ち上がるが、`layer=-1` の掘割や `layer=2` の二階建て高架が同一平面に落ちる。B-1（tunnel）と同時に扱うのが自然。

### B-6. 取得すらしていないが、日本の街の「らしさ」に効くもの

## C. 地形 — 最大の未使用資産

### C-1. 5mメッシュDEMをダウンロードして、545m間隔でしかサンプルしていない ★★★

**該当**: `part5.js:205-258`（タイル取得・デコード）、`part5.js:299-308`（サンプル）、`part6.js:30-50`（グリッド定義）

取得しているのは:

```js
const GSI_DEM_SETS = [
  { name: 'dem5a_png', z: 15 },  // 航空レーザ5mメッシュ
  { name: 'dem_png',   z: 14 },  // DEM10B
];
```

`dem5a` は国土地理院の**航空レーザ測量5mメッシュDEM**。z15 のタイルは北緯35°で約1,002m四方なので、256px で割ると **1px ≈ 3.9m**。しかもコードは既にタイル全体をデコードしている:

```js
const d = ctx.getImageData(0, 0, 256, 256).data;
const out = new Float32Array(65536);           // ← 65,536点の標高が手元にある
for (let i = 0; i < 65536; i++) { ... }
```

ところが、そこから取り出すのは:

```js
const h = tile[j.py * 256 + j.px];             // ← 最近傍1点だけ
```

そしてその1点で埋めるグリッドは:

| グリッド | 範囲 | 分割 | 実質間隔 |
|---|---|---|---|
| NEAR (`part6.js:47-48`) | ±0.06°（約±5.5km） | 20分割（21点） | **約545m** |
| WIDE (`part6.js:30-31`) | ±0.13°（約±14km） | 28分割（29点） | 約1,000m |
| 描画メッシュ (`part5.js:37,49`) | 12,000m | 60分割 | 200m（上記を補間） |

つまり **1タイルあたり65,536点ある標高データから、実際に使っているのは数点だけ**。比率にして数千分の1〜1万分の1。

**なぜこうなっているか**: `part6.js:48` のコメントに「約540〜665m間隔、**約5バッチ(呼び出し回数は据え置き)**」とある。この粒度は**標高が点クエリAPI（opentopodata等）だった時代に、APIコール数を抑えるために決めた値**。GSIタイル方式に移行した後もそのまま残っている。**今は同じタイルを何点サンプルしようが通信量は1バイトも変わらない。**

**realism への影響**: 河岸段丘、切通し、堤防、盛土、谷筋、造成地の段差、坂道の勾配変化 — 「歩いていて分かる地形」がすべて545m間隔の線形補間で均されている。実在の場所を歩く体験としては、建物や道路の忠実度をいくら上げてもここが平らだと嘘が残る。

**着手の順序（重要）**:
1. サンプル密度を上げること自体は**通信ゼロ・コードは局所的**（NEAR_SEGS を 20 → 60〜100 に上げ、`_gsiFetchPass` の点数を増やすだけ）
2. ただし描画メッシュ側（`FAR_STEP = 200m`, `FAR_SEGS = 60`）を細かくしないと、細かい標高データを持っていても画面には出ない
3. `FAR_SEGS` を上げると `updateFarMesh` の再計算コストが二乗で増える。その内側にある `coastGeomAt` は、性能レビューの A-3 対応として **2026-08-27 に空間ハッシュ化済み**（`part4.js:873` `queryPolyGrid(coastlineSegGrid, ...)`、実機確認済み）。**この前提条件は既にクリアされている**ので、残るコストは頂点数そのもの
4. 定石は「プレイヤー近傍だけ細かいメッシュを1枚重ねる」二段構成。近傍200m四方を10m格子（21×21）にするだけでも、足元の地形は別物になる

**これが realism 改善の中で最も伸びしろが大きく、同時に最も前提条件が多い項目。**

### C-2. 標高が2倍に誇張されている

**該当**: `part5.js:134` `const ELEV_SCALE = 2.0;`

すべての標高が2倍。大山（1,252m）は 2,504m として描かれ、**坂の勾配も2倍**になる。日本の住宅街の10%勾配の坂が20%になるので、歩いている時の体感が大きくずれる。

## D. 挙動とスケール

### D-1. 「歩き」が存在しない ★（realism と性能が同じ方向を向く珍しい項目）

**該当**: `part9.js:630-632`

```js
const joyMag = joyActive ? Math.min(1, Math.sqrt(joyOx*joyOx + joyOz*joyOz)) : 0;
let speed = 5 + 40 * Math.min(1, Math.pow(joyMag, 0.7) * 1.15); // 最大45m/s
if (keys['shift']) speed = 45;
```

最低速度が **5 m/s = 18 km/h**。人の歩行は 1.4 m/s（5 km/h）、小走りで 3 m/s（11 km/h）なので、**このゲームには歩行も小走りも存在せず、最も遅い移動が既に全力疾走を超えている**。

さらに悪いことに、`pow(joyMag, 0.7) * 1.15` は原点付近で急峻なので、ジョイスティックをわずかに倒した（joyMag = 0.1）だけで:

```
speed = 5 + 40 × pow(0.1, 0.7) × 1.15 ≈ 5 + 9.2 ≈ 14.2 m/s ≈ 51 km/h
```

**モバイルで実用的に出せる最低速度が約50km/h。**

**副作用（実装済み機能が丸ごと死んでいる）**: `js/core/audio.js:34-37, 269-275`

```js
const RUN_KMH = 8;        // これを超えたら走りストライドに切替
const VEHICLE_KMH = 12;   // これを超えたら乗り物移動とみなし足音を止める
...
if (kmh > VEHICLE_KMH) { _footAcc = 0; return; }
```

最低速度 18 km/h > VEHICLE_KMH 12 なので、**explore（3D探索）モードでは足音が一度も鳴らない**。2026-08-17 に実装した足音機能が、主要モードでは完全に到達不能なコードになっている。GPS追従モード（実際の移動速度を使う）と経路シムでだけ鳴る。

**提案**: 速度を段階化する。
- 歩き 1.4 m/s / 小走り 4 m/s / ダッシュ 45 m/s（現状の shift 相当）
- ジョイスティックは倒し量に比例した連続値（`pow` の指数を上げるか線形に）

**性能レビューとの相乗効果**: 前回レビューで「移動にタイル生成が追いつかない」が繰り返し出てきたが、その前提は「常に50〜160km/hで移動している」こと。歩行速度が使えるようになれば、**同じ生成能力のまま体感の「間に合わなさ」が消える**。realism 改善が性能問題の緩和も兼ねる、数少ない項目。

### D-2. 三人称カメラが遠すぎる／FOVが広い

**該当**: `part7.js:801` `const camDist = 15, camHeight = 8;`、`part1.js:492` `new THREE.PerspectiveCamera(75, ...)`

プレイヤーの **15m後方・8m上空**から、**FOV 75°** で見下ろしている。人間のスケールが失われ、街がジオラマに見える。RPGの俯瞰視点としては妥当だが、「実在の場所を歩く」realism とは方向が違う。

- `camDist` 4〜6m / `camHeight` 1.8〜2.5m
- FOV 55〜65°（75° は広角レンズ相当でパースが誇張される）

一人称モード（`viewMode = 1`）は既に実装済み（`part7.js:844`）なので、**realism を重視するなら一人称を既定にする**という選択肢もある。D-1（歩行速度）とセットで効く。

## E. 質感（中コスト・後回しでよい）

### E-1. マテリアルが全部 `MeshLambertMaterial`

鏡面反射（specular）が一切ないので、窓ガラス・水面・濡れた路面・金属が「色の違う拡散面」でしかない。全部を `MeshStandardMaterial`（PBR）にするのはモバイルには重すぎるが、

- **窓（`facadeMat`）と水面だけ `MeshPhongMaterial`**（`specular` + `shininess`）にする

のは安価で効果が大きい。特に水面に太陽のハイライトが乗ると、水が水に見えるようになる。

### E-2. 接地の暗がり（AO / コンタクトシャドウ）が無い

A-2 と同根。建物・木・小物が地面から浮いて見える。全体の影を入れないなら、せめて足元のブロブ影だけでも入れる価値がある。

### E-3. 屋根テクスチャが 64×64

**該当**: `part2.js:446` `c.width = c.height = 64;`

瓦の段（8px間隔）が近くで見るとぼやける。128 に上げるか、A-3（anisotropy）で改善する。A-3 の方が安い。

### E-4. 建物の壁が上下で均一

`facadeMat` は 128×128（1フロア分）を `sharedFacadeBoxGeo` の UV 繰り返しで積んでいる（`part2.js:371-382`）。つまり**全フロアが完全に同じ**。実際のビルは1階だけ店舗・エントランスで見た目が違う。

`kind === 'house'` には既に「軒下の影」「幕板」「基礎」の描き分けがある（`part2.js:237-242`）ので、office/apt にも「1階だけ別テクスチャの帯を1枚重ねる」ことは可能。ただしジオメトリが1つ増えるので、`detailOK()` のような予算ゲート必須。中コスト。
