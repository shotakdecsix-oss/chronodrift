## 目的

`C:\Users\Shoichi\Desktop\isehara-game` は3D探索アプリ（index.html + js/legacy/part1〜10.js構成、Renderにデプロイ、mainブランチへのpushで自動デプロイ）。

## これまでの経緯・決定事項

### 前提のひっくり返り①：経路シム固有ではない

経路シム以外（通常のWASD探索・BIRDモード）でも落ちることが判明。

### 前提のひっくり返り②：昨日の新機能は原因ではない

ユーザーの「おとといは落ちなかった、昨日GPS追従を入れてから落ちるようになった」という証言を受けて**二分探索を実施**。7/26時点のコミット `26d9b18`（BIRD・GPS追従・経路シムが全部入る前）のクライアントを一時デプロイして再現したところ、**旧バージョンでも移動を続けると落ちた**。

→ クラッシュは以前から存在していた。発動条件は**連続移動そのもの**。昨日の機能（BIRD 3倍速、経路シムの無人自動運転）はクラッシュを作ったのではなく、「止まらず移動し続ける」状況を日常化させただけ。この線は完全に消えた。

なお二分探索は `git checkout 26d9b18 -- js index.html` → commit → push、戻す時は `git revert` で実施した。現在は revert 済みで最新版に戻っている。

### 前提のひっくり返り③（最重要）：THREEのデータ量は原因ではない

`renderer.info.memory` は**個数**しか返さないため、シーン全体のジオメトリ**実バイト数**を測る計器 `[gpuBytes]`（part9.js の `logGpuBytes`、10秒ごと）を追加して実測した。結果：

| | 値 |
|---|---|
| ジオメトリ実バイト数（lite設定） | **14MB** |
| テクスチャ実バイト数（lite設定） | **25MB** |
| 同（std設定） | 29MB / 55MB |
| JSヒープ（usedJSHeapSize） | 100〜640MBで振動、単調増加なし |
| **実際のGPUプロセス** | **約2GB** |
| **実際のレンダラプロセス** | **約1.5GB** |

**GPUメモリの95%以上は、アプリが作っているジオメトリ・テクスチャではない。** liteでもstdでも落ちる。したがってPERFプリセット変更・各種上限・距離アンロードといった「データ量を減らす」方向の対策は原理的に効かない。
