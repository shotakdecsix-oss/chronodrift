# 実装指示: 川の水面が「正しい形」と「正しい高さ」を両立できない問題

作成: 2026-08-03 / 対象: `js/legacy/part4.js`(`_instantiateAreaPolyMesh` / `rebuildAreaPolyMesh` /
`_smoothGroundMinWater` / `processWaterRelation`)、`js/legacy/part5.js`(`farNodeY` / `farSurfaceY`)

---

## 0. 結論

**前提が1つ間違っている。「水中の地形にノイズや起伏がある」という認識が事実と違う。**

地形メッシュは `FAR_STEP = 200m` 格子(`part5.js:37,49`)、その元データは
NEAR で約540〜665m間隔、WIDE で約1km間隔(`part6.js:31,48`)。
**相模川の川幅(200〜500m)は、地形格子1〜3マスぶんしかない。**
つまり川の下に「実測の起伏」は存在せず、あるのは **両岸のノードを200mかけて直線で結んだ
ランプ**だけ。水面に漏れ込んで見えていたのは地形のノイズではなく、**この両岸ランプ**である。

この事実から、失敗の理由が全部説明できる。

---

## 1. なぜ修正3(半径20mの局所最小)が効かなかったか

```js
const WATER_SMOOTH_R = 20;                       // ← 地形格子の 1/10
function _smoothGroundMinWater(x, z) {
  return Math.min(getGroundY(x, z), getGroundY(x±20, z), getGroundY(x, z±20));
}
```

`getGroundY` = `farSurfaceY` は **200m三角形の上の線形補間**(`part5.js:64-73`)。
半径20mの5点は、ほぼ確実に**同じ三角形の内側**に落ちる。
**線形な面の上で min を取っても、ノイズは1つも消えない。** 消すべきノイズがそもそも無い。

起きるのは1つだけ: **勾配 × 20m ぶん、一律に下がる。**
勾配2%なら 0.4m、5%なら1m。yOff は +0.15m しかないので、**水面は確実に地形の下へ潜る。**

> **修正3は「ノイズ除去」ではなく「水面を数十cm下げる処理」だった。**
> だから「直っていない(=まだ地面が突き抜ける)」になった。**この関数は削除すること。**

平滑化半径は、平滑化したい対象の解像度**より大きく**なければ意味がない。
地形が200m格子なら、意味のある平滑化半径は最低でも200〜400m。20mは桁が違う。

---

## 2. 「地面が混ざり込む」の正体は、頂点ではなく**辺**(弦 vs 曲面)

修正1・2の時代の `ShapeGeometry` は、間引き後の輪郭点(間隔数十〜数百m)だけで
三角形を張っていた。**水面の1枚の三角形が、200mの地形三角形を何枚もまたぐ。**

平らな三角形が凸な地形(堤防・中州・河川敷の段差)をまたげば、**頂点の高さがどれだけ
正確でも辺(弦)が必ず地形に切られる。** 三角形の内側から地面が生えて見える。

> **「頂点ごとに正しい高さを取る」方向の努力は、この症状には原理的に効かない。**
> 必要なのは (a) 三角形を地形格子より細かくする、(b) 頂点を地形の**局所最大**より上に置く、の2つ。

---

## 3. 概念の誤り: 水面は0次元でも2次元でもなく、**流下方向の1次元関数**

| | やったこと | 結果 |
|---|---|---|
| 修正1・2 | **0次元**(ポリゴン全体で1つの値) | 長い川では必ずどこかが浮くか沈む(本人も到達済み) |
| 修正3 | **2次元**(各点で地形を追う高さ場) | 地形の嘘(両岸ランプ)をそのまま拾う |
| **正解** | **1次元**(流下方向 s の関数) | 断面方向は完全に平ら、流下方向にだけ緩やかに下る = 実際の川 |

実際の川の水面は「横断方向に平ら・縦断方向に単調に下る」。
**この1次元性を明示的にモデル化していなかったことが、6回失敗した理由。**
0次元と2次元の間を往復していたが、正解はその中間の1次元にある。

---

## 4. 設計(これを実装する)

### 4-1. 高さ: 流下方向1次元プロファイル(縦断形)

```
1) 主軸を決める
   輪郭点 pts のPCA第1主成分(共分散行列の固有ベクトル)。
   簡易版で始めるなら bbox の長辺方向でよい(相模川はほぼ南北なので実用上十分)。
   各点の主軸座標を s とする。

2) ビン分割
   s を BIN = 200m(地形格子と同じ)で分割。

3) 各ビンの水位を「地形の局所最大」から決める
   そのビンに掛かる 200m格子ノード(=地形の真の自由度。中間点を見る意味は無い)
   の terrain 値の最大を M_b とする。+ WATER_MARGIN(0.3m)。
   ★ 修正2は「ポリゴン全体の最大」だった。ビン単位の局所最大にするだけで
     「浮き」は川幅方向の数十cm〜数mに収まり、空中に浮いては見えなくなる。

4) 下流→上流へ累積最大を取る
   for (b = 最下流-1; b >= 0; b--) M[b] = Math.max(M[b], M[b+1]);
   → 流下方向に単調非増加が保証され、かつ どのビンでも局所最大を下回らない。

5) 上向きのみの移動平均で滑らかにする
   M[b] = Math.max(M[b], 前後3ビンの平均)  ← 下げない(下げると突き抜けが復活する)

6) waterY(x, z) = M を s について線形補間した値
```

**この関数は「ビンごとの地形局所最大以上」であることが構成上保証される。**
後述の三角形細分と組み合わせると、**突き抜けゼロが証明できる**(4-3参照)。

### 4-2. 形: ShapeGeometry(earcut)に戻す + 三角形を細分する

- **40m格子分割は即刻やめる。** 「川の形が四角」の原因はこれ以外にない。
  `buildTerrainFollowingAreaPoly` の格子方式は、校庭・田畑のような小さく規則的な形状
  のための簡易対応で、長く曲がりくねった川には使ってはいけない(元コメントの
  「実用上は問題ない」という但し書きが、この用途では成立しない)。
- **輪郭は OSM の `pts` をそのまま ShapeGeometry / earcut に渡す**(holes もネイティブ機能で扱える。
  格子方式で失った hole 対応も自然に戻る)。
- **earcut の出力を細分する**: 最長辺が `MAX_EDGE = 100m`(地形格子200mの半分)以下になるまで、
  三角形を中点分割(1→4)で再帰分割する。輪郭上の辺を分割しても輪郭形状は変わらない
  (中点は元の辺の上に乗るため)ので、**形の忠実性は一切損なわれない。**

```js
function subdivideTriangles(verts, idx, maxEdge) {
  // 辺の中点を共有するため Map<"a,b", newIdx> でキャッシュすること
  // (共有しないと隣接三角形の間に T-junction ができ、髪の毛のような隙間が出る)
}
```

> **T-junction に注意。** 中点を隣の三角形と共有しないと、1ピクセルの筋状の隙間が
> 川面に走る。必ず辺キーでキャッシュして共有頂点にすること。

### 4-3. 突き抜けゼロの保証(なぜこれで直るのか)

- 地形は200mセル上の**線形**関数 → **セル内の最大値は必ず4隅ノードのどれか**で取る。
- 水面頂点の高さは「その点が属するビンの、掛かる全ノードの最大 + margin」以上。
- 水面三角形の辺は100m以下 → 1つの三角形は高々2×2ノードの範囲に収まる。
- よって三角形の3頂点すべてがその範囲の地形最大以上 → **平らな三角形全体が地形以上。**

**margin(0.3m)だけの厳密な余裕で、原理的に地面が出ない。**
今の yOff=0.15 は「頂点だけ」に効いていて辺には効いていなかった。

## 5. 根治案(次の段階): 地形側を彫る

このプロジェクトの `farNodeY` が「メッシュ頂点と `getGroundY` の唯一の共通ソース」に
なっている設計は非常に良い。**ここに水マスクを1つ足すだけで、問題を発生源から消せる。**

```js
// part5.js
function farNodeY(i, j) {
  const h = (typeof terrainY !== 'function') ? 0 : (terrainY(i * FAR_STEP, j * FAR_STEP) || 0);
  const w = waterNodeLevel(i, j);          // Map<"i,j", 水位> のルックアップ1回。水域外は null
  return w === null ? h : Math.min(h, w - WATER_DEPTH);
}
```

- `waterNodeLevel` は、水面ポリゴン到着時に**200m格子ノードを1回だけ** `pointInPolygon` して
  Map に焼く(ポリゴン破棄時に消す)。**毎フレームの多角形内外判定は不要。**
- 地形が構造的に水面より下になるので、水面は4-1の素直な1次元シートでよくなる。
- `getGroundY` は「見えている地面」なので、彫ると**プレイヤーが川に落ちる**。
  プレイヤー・当たり判定用に `surfaceY(x,z) = Math.max(getGroundY(x,z), waterLevelAt(x,z))`
  を用意して差し替えること(未解決の road-submersion にも効く可能性がある)。

**ただし制約を正直に**: 200m格子では、幅300mの川の内側に入るノードが0個のこともある
(川が2ノードの間を通り抜けるケース)。その場合は彫れない。
「水域と交差するセルは4隅すべて彫る」にすると両岸100〜200m陸側まで彫れてしまう。
**相模川のように河川敷が広い川ではむしろ実態に近いが、細い川では堤防が削れる。**
だから 4章(局所最大+細分)を先に入れ、5章は「広い水域だけ」に限定して後から入れるのが安全。

## 6. 質問への直接の回答

**Q1「輪郭はそのまま・高さだけ空間スムージング」は妥当か**
→ **方向は正しいが、それだけでは直らない。** 2章の弦問題があるので、
輪郭を正確に保ったまま**三角形を細分する**工程が必ず要る。
また「スムージング」は現状の半径20mでは無意味(1章)。
やるべきは平滑化ではなく**流下方向1次元プロファイル + 局所最大**(4-1)。

**Q2 突き抜けゼロと浮かないの両立**
→ **両立する。鍵は「グローバル最大」を「ビン単位の局所最大」に変えること。**
修正2が浮いたのは川全体で1つの最大値を使ったから。200mビンごとの最大なら、
持ち上がるのは「その断面の岸の高さ」までで、これは実際の川の見た目と矛盾しない。
そこに単調非増加の制約を入れると、川らしい縦断形になる。
数学的保証は4-3のとおり(地形が区分線形であることを使う)。

**Q3 stitchRings が歪んでいる可能性**
→ **可能性はある。特に「閉じなかったリングをそのまま採用」する分岐が危険。**

```js
if (found < 0) break; // これ以上つながらない → 開いたまま採用(earcutは閉じ扱い)
```

開いたリングを earcut に渡すと、**最後の点と最初の点が直線で結ばれる**。
相模川クラスなら数kmの直線が川面を横切ることになる。
さらに `seenOSMRelations` は**最初に届いたタイルの応答が勝つ**ので、
その応答のメンバーが不完全だと、不完全なリングが確定してしまう。

**切り分け方法(Macなしでできる、決定的)**:
1. `stitchRings` の各リングについて、閉じたか(`_llEq(head,tail)`)を `console.log` する。
   相模川で `closed=false` が出れば、形の問題の少なくとも一部はここ。
2. リングを面ではなく **`THREE.Line`(輪郭線だけ)** で描くデバッグ表示を足す。
   - 線が正しく川の形 → 三角形分割か高さの問題
   - 線自体が歪んでいる/巨大な直線が走る → stitching の問題
   この2つを分けないまま7回目の修正に進まないこと。
3. `thinPts(pts, 25)` は「前の採用点から25m未満なら捨てる」単純間引きで、
   Douglas-Peucker のような形状保存性が無い。**細い所で輪郭が自己交差しうる**
   (自己交差した多角形を earcut に渡すと出力は保証されない)。
   まず tol=0 にして症状が変わるか見るのが最短の切り分け。

**Q4 earcut をやめるべきか**
→ **やめる必要はない。今回の問題は一度も earcut のせいではない。**
中州(hole)付きの凹多角形は earcut の得意分野。
やるべきなのは分割器の交換ではなく、**入力の健全化(Q3)と出力の細分(4-2)**。
入力が自己交差していたり開いていたりすれば、どのライブラリでも結果は壊れる。

## 7. 実装順(1つずつ出して実機確認)

| # | 内容 | 期待される変化 | 規模 |
|---|---|---|---|
| 1 | `stitchRings` の閉/開ログ + 輪郭Line デバッグ表示 + `thinPts` tol=0 テスト | **形の問題の切り分け**(高さと混ぜない) | 小 |
| 2 | 40m格子をやめ ShapeGeometry へ戻す + 三角形細分(maxEdge=100m、中点共有) | 「四角い川」が直る。弦切りが消える | 中 |
| 3 | `_smoothGroundMinWater` を削除し、1次元プロファイル `waterY(s)` に置換 | 浮き・突き抜けが同時に直る | 中 |
| 4 | (広い水域限定)`farNodeY` の水マスクで地形を彫る + `surfaceY` | 構造的に発生源が消える | 中 |

**必ず守ること**: 高さ計算は `_instantiateAreaPolyMesh`(新規)と `rebuildAreaPolyMesh`
(NEAR更新時)の**両方**が同じ関数を通ること。
2026-08-03に一度これで失敗している(片方だけ直して、NEAR更新のたびに古い計算が上書きし戻した)。
今回は `waterY` をポリゴンの `entry` にプロファイル配列ごとキャッシュし、
両方がそれを参照する形にすれば、構造的に食い違わなくなる。

## 8. 大原則への追記

10. **平滑化・サンプリングの半径は、対象データの解像度と必ず突き合わせて決める。**
    地形が200m格子なのに半径20mで平滑化する、のような桁違いを防ぐ。
    定数を置くときは「元データの解像度は何mか」をコメントに書く
    ([[feedback_pair_check_distance_constants]] の水平方向版)。
11. **面を地形に合わせるときは、頂点だけでなく辺(弦)も評価する。**
    頂点が正しくても、地形格子より大きい三角形は必ず地形に切られる。
12. **実データが存在しない量(水底標高)は、存在するデータ(岸の標高)と
    物理的性質(水面は横断方向に平ら・縦断方向に単調)から構成する。**
    無いデータを周辺補間で代用した値をそのまま使わない。
