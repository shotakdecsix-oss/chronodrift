# 引き継ぎ: タイル取得レイテンシ改善(chronodrift / isehara-game)

以下は前のチャットからの引き継ぎ内容です。この続きから対応してください。

## 目的(ずっと変わっていない本題)

ブラウザ3Dマップゲーム `chronodrift.onrender.com` で、**プレイヤーの足元と周囲のタイルの道路・建物が出るまでが遅い**。デバッグオーバーレイの色遷移で言うと:

- **R = 緑赤灰 → 緑緑赤** … キュー投入 → 道路確定
- **B = 緑緑赤 → 緑緑黄** … 道路確定 → 建物確定

### 要件(2026-07-26にユーザーが明示。初期ロード時またはマップジャンプ時)

- **tier1**(現在地1枚): 5〜10秒以内に地形・道路・建物すべて完了
- **tier2**(3x3外周8枚): 道路10秒以内 / 建物20秒以内
- **tier3**(5x5外周16枚): 道路30秒以内 / 建物60秒以内
- **tier4**(それ以遠): 上記達成後のベストエフォート

## 環境・進め方の制約(再確認不要)

- 会話は日本語。トークン消費は最小限に。手動でできることは依頼する
- WindowsのPowerShellが5.x以前。コマンドは `&&` ではなく `;` 区切り
- **push コマンドには必ず `Remove-Item -ErrorAction SilentlyContinue ...\.git\index.lock;` を前置する**
- Render 無料プラン。15分でスピンダウン、コールドスタート約39秒、ディスクは揮発。main への push で自動デプロイ
- **push成功 ≠ デプロイ完了。** `https://chronodrift.onrender.com/api/ping` の `deploy` ハッシュだけが信頼できる判断材料。画面の「デプロイ日時」表示は当てにならない(時刻はプロセス起動時刻、括弧内はコミット時刻)。実際に一度、GitHubには届いたのにRenderが自動デプロイしない取りこぼしが起きた。その時は Render Dashboard → Manual Deploy → "Deploy latest commit"
- ユーザーは**別のレビュアーAIの指摘を持ち込む**。断定する前にコードで裏を取ること

## 構成のポイント(誤解しやすい所)

`server/server.js` は serve 時に `index.html` へ `<script>` を注入(INJECT)し、`window.fetch` を monkey-patch して `https://overpass-api.de/api/interpreter` を `/api/overpass` に書き換えている。**クライアントソースを grep してもプロキシ経路は出てこない。**

INJECT はテンプレートリテラルなので、正規表現リテラルを書くと `\/` が `/` に潰れて壊れる(過去に事故あり)。**検証は必ず「評価後の出力形」に対して行うこと。**

## 前回セッション(2026-07-26)で起きたこと

**一日の大半は「実在するインフラ障害を、自分のコードのバグとして追っていた」。** 途中で道路も建物もまったく生成されない状態になり、真因は **RenderのegressがOverpass側にIP拒否されていたこと**だった。

`/api/upstream-status` で確定:

- `overpass-api.de` … Aレコード2台(`65.109.112.52` / `162.55.144.139`)**とも `ECONNREFUSED`**
- `overpass.private.coffee` … `upstream timeout`
- **同時刻に、ユーザーのPC・モバイル回線からは `/api/status` が200で「2 slots available now」**

→ サービスは健全。拒否されているのはRenderのIPだけ(無料プランの共有NATで巻き添えの可能性が高い)。

### 復旧方法(適用済み・デプロイ済み・動作確認済み)

`OVERPASS_MIRRORS` の先頭を **VK Maps** (`https://maps.mail.ru/osm/tools/overpass/api/interpreter`) にした。Renderから200が返り、しかも **`Rate limit: 0`(上限なし)**。OSM Wikiにも "There are currently no requests limitations" と明記。**これで道路・建物とも正常に生成されるようになった。**

### 併せて確定した事実(すべて現行コードに反映済み)

- **RenderのコンテナにIPv6経路が無い**(`ipv6Probe` が `ENETUNREACH`)。Node 18以降はIPv6を優先するため、上流リクエストは `family: 4` 固定。**外すと全滅する**
- `httpsRequestOnce` はAレコードを全件引いてラウンドロビンし、接続レベルのエラーなら次のアドレスへ回す(片系統だけ落ちるパターンへの保険。今回の主因ではなかった)
- **`overpass.kumi.systems` と `overpass.private.coffee` は同一サービス**(Wikiに "Previously known as" と明記、DNSも同一IP `193.219.97.30`)。名前3つでも実体2系統だった
- 有料の選択肢として Geofabrik(APIキー制)がある

### 生成が止まったときの切り分け手順

1. `https://chronodrift.onrender.com/api/upstream-status` を開く
2. `upstream` に `ECONNREFUSED` / `timeout` が並んでいたら**経路の問題。コードを触らない**
3. ユーザーのPCから `https://overpass-api.de/api/status` が開けるかと対比する。開けるならIP拒否、開けないなら先方の障害

## 最重要: 設計の土台が変わった

**今日までの全ての判断は「上流Overpassは1IPあたり2スロット固定」の上に乗っていた。VK Maps は `Rate limit: 0` = 上限なしなので、この前提が当てはまらない。**

再評価の対象:

- `UPSTREAM_WORKERS = 2`(server.js)と `OSM_TILE_CONCURRENCY = 2`(part8.js)は、いま人為的な足かせでしかない可能性が高い
- 案A(先読み削減 `PERF.prefetchR` 2→1)、案B(条件節削減)、案C(道路クエリの2段分割)はすべて「2スロットの中でどうやりくりするか」の話だったので、前提から見直しになる
- 要件に足りない**3.6〜3.9倍**は、並列度を上げるだけで届く射程かもしれない

## 次にやること(この順序を推奨)

**1. 分離クエリのA/B(1分で終わる。並列度を触る前にやる)**

コンソールで `window.SPLIT_NEAR_QUERIES = false;` → **マップジャンプ**。戻すときは `= true;` → ジャンプ。スイッチは実装済み・デプロイ済み。

背景: ユーザーが「以前のデプロイの方が、足元タイルの遅れはあったけどもっと快適に遊べていた」と証言。履歴を追うと `ai-consult-tile-query-architecture-prompt.md`(07/24 14:57)→ `IMPL_PROMPT_20260724_TILE_QUERY_ARCH.md`(16:51)→ コミット `07523fe`/`c240b58`(17:13/17:26)の **道路/建物クエリ分離**が該当。この変更で近傍3x3のリクエストが **9本→18本**になり、足元タイルの完成が **1往復→2往復の直列**になった(建物ジョブは道路確定後にしか積まれない)。

**注意: 単純に旧コミットへ巻き戻してはいけない。** 旧 `part8.js` は `&priority=` を送らず、現行 server.js が未指定を `PRIO_RANK.far` として扱って `FAR_INFLIGHT_MAX` で絞るため、分離とは無関係な理由で遅くなりA/Bが成立しない。また `server/` を戻すと直接モードが復活して致命的。だから分離だけを切るスイッチを用意してある。

**2. 並列度を上げてどこまで速くなるか試す**

`UPSTREAM_WORKERS` と `OSM_TILE_CONCURRENCY` を上げる。VK Maps に上限が無いので、以前のような429ストームにはならないはず。1の比較条件が変わるので必ず1の後に。

**3. 別件のバグ(未調査)**

キューの `tier4` が常時 **116〜120件 / 全137件** 溜まっている。進行方向の先読みが `k=3..6`(最大9600m先)まで積んでおり、処理能力を大きく超えている。これらは `queuedTiles` に登録済みなので「**永久に実行されないのに取得済み扱いでマークされたタイル**」が生まれ、プレイヤーがそこへ歩いた時に再投入されず白紙のままになる恐れがある。レイテンシとは別のバグ。

なお計測2回とも稼働枠の占有は `tier1 + tier1+ + tier2 = 100%` / `tier3 = 0%` / `tier4 = 0%` だったので、**案A(先読み削減)はレイテンシ対策としては2回とも否定されている**。ただし上記の白紙バグは別途残る。

## 計測ツールと、その使い方の注意

`DEBUG_PROBE_TILE_LATENCY.js` をコンソールに丸ごと貼り付け → `TP.report()`。

- **必ず「プローブを貼ってから、ジャンプする」順序で。** プローブは計測開始後にキュー投入されたタイルだけを対象にするため、逆順だと R/B が全部「データなし」になる(実際に一度やらかした)
- 設定は **std に固定**(high は `prefetchR` が 3 になり 7x7 になるので比較不能)
- 健全な計測の条件: `経由: PROXY=N / DIRECT=0 / 例外=0`。`DIRECT` か `例外` に数字が入っていたらその回のデータは使わない
- `完了時間` は **クライアント側の待ちは除くが、サーバー側の待ちは含む**。server.js は host ごとに `UPSTREAM_WORKERS` と `MIN_INTERVAL_MS=1100` の待ち行列を持つため、「Overpassが1クエリを実行するのに何秒か」はこの値からは分からない

## tier の定義(probeのラベルとコードの実装は1対1ではない)

probe側は `OSM_TILE_M = 1600` のチェビシェフ距離: tier1=d0(1枚) / tier1+=d1のうちblocking格上げ分 / tier2=d1の残り / tier3=d2(16枚) / tier4=d3以遠。

コード側が実際に区別している境界は3つだけ:

- `_blockingTiles` … 足元64m圏 + ring1の最近接1枚を格上げ(スコア -100000)。**tier1とtier2にまたがる**
- `NEAR_SPLIT_TIER_R = 1` … 3x3。道路/建物分離ゾーン、かつ `nearSolo` でソロ固定(スコア -10000)。**コードはtier1とtier2を区別していない**
- `NEAR_TIER_R = 2` … 5x5(スコア -9000)

ズレやすい点: 建物ジョブ(`kind='building'`)は距離に関係なく常に tier2帯。`osmTileActiveFarCount` は tier とは別物(実行レーンの話)。probeのtierは観測時点のプレイヤー位置で決まる。

## 試して駄目だったこと(繰り返さない)

- **「プロキシは死にコード」誤診断** … クライアントをgrepしてヒットしなかったため。実際はINJECTのmonkey-patch
- **`maxAttempts` 2→4** … 成功率が 38%→24% に悪化。2に戻した
- **タイムアウトを到達不能判定に使う** … 2段階で試してどちらも密集地の起動直後に誤爆。撤去した
- **`overpass.private.coffee` をメインにする** … 当時は失敗。※ただし今はVK Mapsがメインで成功している
- **tier2の道路/建物ジョブを3枚まとめにする(Step C)** … revert済み。ただし当時のA/Bは経路が違ったので比較として不成立
- **Overpassの既定を直接アクセスにする** … 撤回済み。ユーザーのIPからも繋がらないことがあり致命的。`NO_DIRECT_FALLBACK[OVERPASS_PREFIX]=true` を迂回していたコールドスタート分岐の穴も塞いだ
- **案A(先読み削減 `prefetchR` 2→1)** … 稼働枠の占有計測で tier3/tier4 が 0% と2回連続で出たため、レイテンシ対策としては否定済み

## 前回、同じ形の誤りを繰り返した記録(教訓)

計測するたびに計測自体が間違っていたと判明し、前の結論を撤回することを5回繰り返した。共通の原因は **n=2のサンプルで結論を出そうとしたこと**と、**片方の経路の失敗だけを数え落とす計器**。

- 「Renderのegressが6〜7割失敗」→ `CONN_FAIL_CODES` の誤分類だった
- 「直接83% / プロキシ24%」→ プローブのfetchラッパーが `await` をtryで囲っておらず、**例外を投げたリクエストを1本も集計していなかった**。プロキシの失敗は502という「レスポンス」なので計上され、直接モードの失敗はthrowなので不可視だった(修正済み)
- 「ソロ1本8.6秒」→ 無効なDIRECTモードの値だった
- 「完了時間はキュー待ちを含まない」→ サーバー側の待ちを含んでいた

**教訓: 数字を出す前に、その計器が両方の経路の失敗を等しく数えているかを確認する。n が小さい間は「まだ分からない」と言う。**
